# Coding Standards (review rulebook)

As of 2026-11-02. Rationale, sources and the conflict table are in `docs/research/rust-standards.md`. This file is first of all the rulebook for code reviews; implementers use it as a reference. Decisions in `docs/adr/` and terms in `GLOSSARY.md` take precedence over it. The rendered UI is reviewed against `UX_STANDARDS.md`.

Stack in one line: a Cargo workspace (edition 2024) with the core crates `crates/model`, `format`, `verify`, `scan` and `engine` (ADR 0004) and the Tauri 2 shell `app/src-tauri`, plus the UI in `app/ui`: React 19, React Flow 12, elkjs in a Web Worker, shadcn/ui on Base UI, Tailwind v4 and Zustand v4, with bindings generated by ts-rs. Tools: rustfmt, Clippy, cargo test, cargo-deny, proptest, insta, cargo-fuzz; strict tsc, Oxlint, Oxfmt, Vitest, Playwright. No Effect, no TanStack Query. "Core crates" means the five crates under `crates/`.

## How to review

1. Read this whole file before you look at the diff. Then check the diff against every rule whose area it touches.
2. Every finding names the rule ID (e.g. `LIM-1`) and `file:line`. Claims about behavior need evidence in the code.
3. **must** blocks the merge. **should** is a note, at most 5 per review. Deviating from a should rule is fine when the PR explains why.
4. **[auto]** rules are enforced by the `check` command (G-2). Report them only when the diff disables, loosens or bypasses a gate, or the gate is not set up yet.
5. Do not report formatting, taste without a rule, or suggestions for more abstraction. Unneeded complexity is itself a finding (G-1).
6. If a rule contradicts an ADR or `GLOSSARY.md`, report the contradiction instead of guessing.
7. ✅ marks the expected pattern, ❌ the pattern to report. A tag at the end of a rule names its source, e.g. `(TigerStyle)`, `(Google)`, `(MS M-PANIC-ON-BUG)`, `(API C-CASE)`, `(raubritter R-3)`, `(ADR 0006)`. Untagged rules are project decisions.
8. Some must rules end with **Why:**, one sentence on the failure the rule prevents. Use it to recognize variants the rule text does not list, not to skip the rule.
9. In this file, "rule" and "finding" mean review rules and review findings, and `check` is the build command. In code these words keep their glossary meanings (anti-pattern Rule, scan Finding, Check of a property).

## Goals

The rules serve these goals, in this order. When no rule covers a case, or a rule can be read two ways, decide by the higher goal. Do not invent new rules in a review.

1. **No wrong verdict, no lost file.** A wrong Proved must never happen, a Disproved always has a replayed counterexample, and an Unknown always says why. A user's project files are never corrupted or lost. Must rules that serve this goal have no exceptions without an ADR.
2. **Clear to the next reader.** A maintainer or agent who opens a file after months understands what it does and why, from the file and `GLOSSARY.md` alone.
3. **Simple.** The smallest solution that meets today's need, for one developer and one local user. Abstraction for later is a cost, not a safeguard (G-1).
4. **Consistent.** One way per concern, so a diff can be compared with the examples here.

**Sources and precedence.** Sources are the Google Rust style guide (https://google.github.io/styleguide/rustguide.html), TigerStyle, other Rust guides (Microsoft Pragmatic Rust Guidelines, Rust API Guidelines) and Clean Code. The React/TypeScript rules are adapted from the raubritter project. Precedence by topic: TigerStyle wins on safety, limits, assertions and control flow; Google wins on style, naming, formatting and API design; other Rust guides fill gaps; Clean Code comes last.

How the precedence plays out:
- Control flow goes to TigerStyle: no recursion, and nested `if`/`else` instead of compound conditions, so Clippy's `collapsible_if` is off (LIM-3).
- Naming goes to Google: acronyms are written as words (`VsrState`, not TigerStyle's `VSRState`).
- API design goes to Google: borrow instead of using TigerStyle's out-pointers (API-1).
- Limits go to TigerStyle, except that TigerStyle's static allocation at startup is dropped, because a model grows while the user edits. Its intent, that nothing grows without a bound, is LIM-1.
- Assertions go to TigerStyle, adapted: the density target applies to core crates only (SAFE-1).
- TODO comments: TigerStyle's zero technical debt wins over Google's `TODO` with a bug link. A TODO marks known-incomplete behavior in merged code, which is a safety question; Google's rule only says how a TODO is written (G-4).
- Comments: TigerStyle's and Google's "say why" wins over Clean Code's "comments are failures" (G-3). Functions may be up to 70 lines (TigerStyle); Clean Code's tiny functions lose.

Core crates are library code, so Google's API rules bind them (API-1). `app/src-tauri` and `app/ui` are application code: they favor directness over reuse.

## G – Principles

- **G-1 must** No over-engineering: one developer, one local user. The following are not used without an ADR:
  - an async runtime or `async` in core crates
  - a trait, trait object or generic parameter with a single implementation
  - plugin or extension mechanisms, or proc macros
  - workspace crates beyond ADR 0004
  - a second state library next to Zustand, or Effect, TanStack Query, Redux, XState or RxJS
  - your own abstraction layer over React Flow or shadcn/ui
  - feature flags or settings with only one value in use
  - caches without a measurement

  Use closed sets as enums, and traits only for real extension points; Google says not to use traits merely to organize code. (TigerStyle, Google, raubritter G-1)

  Why: one developer maintains every layer alone, and an abstraction built for later is paid for today and rarely fits the later need.
- **G-2 must [auto]** `check` is green, and the configuration is the rule.
  - `check` runs: rustfmt, Clippy with the workspace lints and `-D warnings`, cargo test (proptest; insta fails on pending snapshots), cargo-deny, the ADR 0004 boundary check, the ts-rs bindings diff, tsc, Oxlint, Oxfmt and Vitest.
  - CI also runs the TAPAAL corpus as a merge gate. cargo-fuzz runs nightly and is not a merge gate.
  - A diff that loosens a configuration is a finding. A single exception uses `#[expect(lint, reason = "…")]` in Rust, or an Oxlint disable comment with a reason, scoped to one item.

  The Rust essentials are in the appendix. (TigerStyle, MS M-LINT-OVERRIDE-EXPECT)

  Why: a gate that one PR may loosen protects nothing in the next one.
- **G-3 should** Comments explain *why*: an invariant, a rejected alternative, a source (ADR, paper, TAPAAL behavior). They never explain *what* the next line does.
  - Public items of core crates have doc comments, with `# Errors` and `# Panics` sections where they apply [auto].
  - No doc comment repeats the item's name and type.

  ```rust
  // ✅ Breadth-first so the first violation found has a shortest counterexample (VRD-2 replay).
  // ❌ increment the counter
  /// ❌ Returns the marking.
  ```
  (TigerStyle, Google)
- **G-4 must** No `TODO`, `FIXME` or `XXX` comments and no commented-out code in merged code. Unfinished work becomes a GitHub issue, linked in the PR; old code lives in git. `todo!`, `unimplemented!` and `dbg!` are **[auto]**; comments are checked in review. (TigerStyle, raubritter G-4)

  Why: a TODO in `verify` is a known soundness gap that nobody tracks, and commented-out code drifts from renamed types while agents copy it back.
- **G-5 must** One concern per PR: a format change, a refactor and a feature are three PRs.
  - Every new crate or npm package is justified in the PR: what it is for, why std or about 50 lines of our own code are not enough, maintenance status and license. Use `default-features = false` where possible.
  - Shipped code contains no GPL or AGPL code, and LGPL only with an ADR. cargo-deny checks crate licenses [auto]; npm licenses are checked in review.
  - Dual-licensed packages are used under the permissive option, e.g. elkjs under EPL-2.0.
  - TAPAAL runs only in CI and is never linked or bundled.

  (raubritter G-2, TigerStyle, ADR 0008)

  Why: a mixed PR hides a format change inside a refactor, and every dependency is code the one developer must audit and update for years.

## ARCH – Layering

- **ARCH-1 must** Dependencies follow ADR 0004 as amended by ADR 0009.
  - `net` holds only data types, constructors, structural validation and canonical encoding: no firing rule, no predicate evaluation, no flattening.
  - `verify` and `recheck` each depend only on `net` and implement the semantics (firing, capacities and when full, predicates, composition) separately from the same written spec. `recheck` never depends on `verify` or `engine`.
  - Neither knows about elements, levels or C4. The map back to elements lives in `engine`.
  - Core crates have no Tauri or tokio types. They use std threads and an `AtomicBool` cancel flag.
  - `model` does no IO, and file IO lives only in `format`.

  cargo-deny bans and a `cargo tree` step enforce the crate graph [auto]. Review checks the semantics: C4 concepts leaking into `verify` or `recheck`, logic added to `net`, IO in `model`.
  ```
  app/ui ──IPC──▶ app/src-tauri ──▶ engine ──▶ format ──▶ model
                       │               ├──▶ scan ──▶ model
                       │               ├──▶ verify ──▶ net
                       │               ├──▶ recheck ──▶ net
                       └──▶ model      └──▶ model
  ```
  (ADR 0004, 0009)

  Why: a Tauri-free, C4-free `verify` is what lets us test it headless, cross-check it against TAPAAL on plain nets and put a CLI on `engine` later.

## SAFE – Assertions, panics and errors

- **SAFE-1 must** In core crates, every non-trivial function asserts its preconditions, postconditions and invariants, about two assertions per function on average.
  - Pair assertions across boundaries: validate a model before it is written and after it is read, and assert both what must and what must not happen.
  - Use `assert!`, which stays on in release (ADR 0006). `debug_assert!` is only for a check whose cost was measured; the measurement goes in a comment, and a property test also covers the invariant.
  - Split compound assertions. Every assertion and `expect` states the invariant [auto: `missing_assert_message`]. Relations between constants are asserted at compile time.

  ```rust
  // ✅
  const _: () = assert!(usize::BITS >= 32, "PlaceId(u32) must fit in usize");

  pub fn fire(net: &PetriNet, marking: &mut Marking, transition: TransitionId) {
      assert!(net.is_enabled(marking, transition), "fire: {transition:?} is not enabled");
      // …
      assert_eq!(marking.len(), net.place_count(), "fire: marking lost or gained a place");
  }
  // ❌ compound, no message
  assert!(net.is_enabled(marking, transition) && marking.len() == net.place_count());
  ```
  (TigerStyle, ADR 0006, Google, MS M-PANIC-MESSAGE)

  Why: an assertion turns a silent wrong state into a crashed check that ends as Unknown (SAFE-4), instead of a wrong Proved.
- **SAFE-2 must** Panics are only for bugs.
  - Malformed files, invalid IPC input, IO failures and exhausted budgets are `Result`s or Unknown verdicts, never panics.
  - No `unwrap` outside tests [auto]. `expect` names the invariant that makes it safe. Prefer `let … else` over check-then-unwrap.
  - Code that parses project files or IPC input does not panic on any input.

  ```rust
  // ✅
  let place = net.place(id).expect("flatten() only emits IDs of places it created");
  let Some(element) = model.element(&id) else { return Err(EngineError::UnknownElement(id)) };
  // ❌ a hand-edited file crashes the app
  let element: ElementFile = toml::from_str(&text).unwrap();
  ```
  (Google, MS M-PANIC-ON-BUG, MS M-PANIC-IS-STOP)

  Why: a panic on the main thread ends the app (ADR 0006), so a panic that user data can reach turns one bad file into a crash on every open.
- **SAFE-3 must** Errors are typed and never discarded.
  - Each core crate that can fail has its own `thiserror` enum. Its variants carry context (path, element ID, line) and the source error.
  - No `String` errors and no `Box<dyn Error>` in core APIs; `anyhow` only in tooling and tests.
  - Tauri commands return one serializable error enum tagged by `kind`, which TS matches exhaustively (TS-1).
  - Errors are handled or propagated, never dropped with `let _ =`, `.ok()` or `map_err(|_| …)` [auto].

  ```rust
  // ✅ crates/format
  #[derive(Debug, thiserror::Error)]
  pub enum FormatError {
      #[error("could not read {path}")]
      Read { path: PathBuf, #[source] source: io::Error },
      #[error("{path}: format version {found} is newer than this app supports ({supported})")]
      VersionTooNew { path: PathBuf, found: u32, supported: u32 },
  }
  // ❌
  pub fn load(dir: &Path) -> Result<Project, String>
  ```
  (MS M-APP-ERROR, Google, TigerStyle, Tauri)

  Why: an error without its path cannot become the message UX TXT-2 requires, and a dropped error looks like a successful save.
- **SAFE-4 must** Never `catch_unwind` [auto: `disallowed-methods`].
  - Each check runs on its own named worker thread. The thread owns an immutable snapshot of the model and shares no locks with the app.
  - If joining the thread returns `Err`, the check ends as Unknown with the reason "internal error", and the panic is logged locally.
  - Release builds keep `panic = "unwind"` [auto].

  ```rust
  // ✅ crates/engine
  let handle = thread::Builder::new()
      .name(format!("check-{check_id}"))
      .spawn(move || run_check(&snapshot, budget, &cancel))?;
  match handle.join() {
      Ok(verdict) => verdict,
      Err(_panic) => {
          // log locally (ADR 0006); the worker's state is discarded with the thread
          Verdict::Unknown(UnknownReason::InternalError)
      }
  }
  // ❌
  let verdict = panic::catch_unwind(|| run_check(&snapshot, budget, &cancel));
  ```
  (ADR 0006, Google)

  Why: no state survives a panicked check, so nothing half-updated can feed a later verdict.
- **SAFE-5 must [auto]** Every core crate root starts with `#![forbid(unsafe_code)]`, and the workspace denies `unsafe_code` everywhere else. Lifting this needs an ADR, a separate small crate, a `// SAFETY:` comment on every block and Miri in CI. (Google, MS M-UNSAFE)

## LIM – Limits, integers and control flow

- **LIM-1 must** Everything that grows with external input has an explicit bound: every exploration, queue, channel, collection and loop.
  - In `verify` and `engine`, the bound is the check's budget plus the cancel flag. Elsewhere it is a named constant with a why-comment.
  - Use `sync_channel(n)`, not unbounded channels.
  - When a check hits a bound, it ends as Unknown with a reason that names the bound. It never ends as Proved and never silently truncates its result.
  - A loop that is meant to run forever says so in a comment.

  ```rust
  // ✅
  while let Some(marking) = frontier.pop_front() {
      if cancel.load(Ordering::Relaxed) {
          return Verdict::Unknown(UnknownReason::Cancelled);
      }
      if markings_explored >= budget.markings_max {
          return Verdict::Unknown(UnknownReason::BudgetExhausted { markings_explored });
      }
      markings_explored += 1;
      // …
  }
  // ❌ unbounded: runs until memory is gone, or until someone adds `break` and falls through to Proved
  while let Some(marking) = frontier.pop_front() { … }
  ```
  (TigerStyle, ADR 0008)

  Why: "no violation found before the budget ran out" is exactly the result that looks like a Proved.
- **LIM-2 must** Input is checked against limits before anything is allocated for it.
  - On load: file size, and element, place and transition counts.
  - On every IPC command: string lengths and collection sizes.
  - Limits are named constants with headroom above the performance targets (300 elements per view, 2,000 per project).
  - Exceeding a limit is an error with a message, never a panic and never an out-of-memory crash. Third-party parsers (TOML) only see input that already passed the size check.

  (TigerStyle)
- **LIM-3 must** No recursion in core crates. Traversals (reachability, drill-down, flattening, cycle detection in `scan`) use an explicit stack or queue, bounded per LIM-1.
  - Control flow is simple and explicit: nested `if`/`else` instead of compound conditions, and every `if` considers its `else`.
  - A `match` on our own enums lists every variant instead of `_`.
  - Functions have at most 70 lines [auto]. No function is split only to get shorter.

  ```rust
  // ✅
  let mut stack = vec![root];
  while let Some(id) = stack.pop() {
      // …
      stack.extend(model.children(id));
  }
  // ❌
  fn collect(model: &Model, id: ElementId, out: &mut Vec<ElementId>) {
      for child in model.children(id) { collect(model, child, out); }
  }
  ```
  (TigerStyle)

  Why: Rust does not guarantee tail calls, and a stack overflow aborts the whole process instead of panicking, so ADR 0006 cannot turn it into Unknown.
- **LIM-4 must** Integer types are explicit.
  - Domain IDs, counts, capacities and token counts are explicitly sized newtypes over `u32` or `u64` (`PlaceId(u32)`). `usize` is only an in-memory index.
  - Conversions use `try_from` [auto: `cast_possible_truncation`].
  - Arithmetic that user data can overflow uses `checked_*` and handles `None`. Release builds keep `overflow-checks = true` [auto], so any other overflow crashes instead of wrapping.

  ```rust
  // ✅
  let place_count = u32::try_from(places.len()).expect("LIM-2 caps places far below u32::MAX");
  // ❌ silently truncates
  let place_count = places.len() as u32;
  ```
  (TigerStyle, Google)

  Why: a wrapped token count makes an overflowing place look almost empty, and a check on that marking can claim Proved.

## VER – Verdict honesty

- **VER-1 must** Code constructs Proved only through the two evidence paths of ADR 0008 as amended by ADR 0017: a certificate (in v1 only `NoOverflowPlace { drop_places }`; P-invariant bounds later) accepted by `recheck::check_certificate` on recheck's own composition of the open nets, or agreement of `recheck::explore` with `verify` (net-semantics §9.4, §9.5). There is no third path; a new certificate kind needs an amendment of net-semantics §9.5 first.
  - The type system enforces this. The verdict the worker returns is `engine::check::Verdict` (design §3, D-53): it holds `CheckedProof` or `CheckedViolation` with private fields, and their only constructors live in those two paths (and, for Disproved, after `recheck::replay`). The `NetVerdict` that `verify::check` and `recheck::explore` return is a candidate and is never cached, shown or converted to a DTO. A new constructor is a finding.
  - A Disproved whose violation is not a finite run needs the same agreement: no dead transitions (`Evidence::Exhaustive`, equal dead sets and marking counts) and the exhaustive part of always reachable (`CounterexampleThenExhaustive`: no p-marking and no overflow marking reachable from the replayed last marking).
  - The second explorer stays a plain breadth-first search with no reductions. It runs on its own composition of the open nets (`recheck::compose`) and shares no code with the main explorer beyond the `net` types.
  - The second explorer gets the markings verify did not use and the remaining wall clock (ADR 0010, decisions D-17). If it runs out, the verdict is Unknown "budget exhausted while re-checking". If it disagrees, or a certificate is rejected, the verdict is Unknown "internal disagreement" and the case is logged.

  ```rust
  // ✅
  pub enum Verdict {
      Proved(CheckedProof),          // Technique::Exhaustive (agreement) or Technique::Certificate (accepted)
      Disproved(CheckedViolation),   // Counterexample (replayed), Exhaustive or CounterexampleThenExhaustive (confirmed)
      Unknown(UnknownReason),
  }
  /// Built only after `recheck::check_certificate` accepted or `recheck::explore` agreed.
  pub struct CheckedProof { technique: Technique, markings: u64 } // private fields: no other module can build one
  // ❌ a shortcut around the evidence path
  if frontier.is_empty() { return Verdict::Proved(CheckedProof::exhaustive()); }
  ```
  (ADR 0008, ADR 0017, GLOSSARY Proved, Certificate)

  Why: a wrong Proved is the one failure the tool must never have, and a single unchecked path is enough to produce one.
- **VER-2 must** Disproved with a counterexample is built only after `recheck::replay` has replayed it on recheck's own composition and it reaches the violation (net-semantics §9.3); for a scope with a state machine, `engine::sm_replay` then checks it in state machine terms (slice 2). The run of an Unknown "capacity exceeded first" is replayed the same way. A replay that fails ends as Unknown "internal error" and is logged; "internal disagreement" is reserved for the two compositions, the two explorers and a rejected certificate.
  - An evidence kind or certificate kind that does not match the property kind is Unknown "internal error".
  - `recheck::replay` and `engine::sm_replay` are evidence checks; the glossary's Replay is the canvas act.

  (ADR 0008, ADR 0010, ADR 0017)
- **VER-3 must** Unknown always carries exactly one reason from the closed enum of ADR 0017, in this order: model incomplete, property cannot be checked, internal disagreement, internal error, cancelled, budget exhausted (main or re-check phase), capacity exceeded first. It is never a free string and never empty. "No counterexample up to depth N" and "unsupported construct" are not reasons; a new reason is an ADR amendment and an IPC change.
  - Every early return, error, cancellation, budget end and panicked join in a check ends in exactly one verdict. The reason is the event that ended the pipeline (net-semantics §10.2).
  - `Verdict` has exactly three variants. A running check is a job state, not a verdict. Nothing to check (`KeyState::NothingToCheck`) is a key state with no verdict, never an Unknown.
  - An Unknown is never cached and never rendered as success.

  (GLOSSARY Unknown, ADR 0006, ADR 0013, ADR 0017)
- **VER-4 must** Verdicts are never written to the project.
  - The CheckKey covers the canonical encoding of the flattened net and of the property, and excludes layout, display names and assumptions. A layout change therefore never makes a verdict stale and never cancels a check.
  - The predicate is hashed as parsed: no code rewrites equivalent spellings (`p > 50` and `p >= 51` have different keys).
  - The final predicate is part of `NetProperty::DeadlockFree { final }`, never of the net, so editing done when changes only the deadlock-free keys and, from slice 4, the keys of "can always get back to: done" template properties, whose expansion is the final predicate (ADR 0022).
  - A scan produces findings, never verdicts. A rule that lacks data reports Not checkable, never Unknown. Findings carry the scan input hash, and a different hash renders them stale.

  (ADR 0005, ADR 0013, ADR 0018, ADR 0019, ADR 0021, ADR 0022, GLOSSARY)
- **VER-5 must** What the verdict panel shows is what was checked.
  - A property template is stored by kind, version and parameters and expanded at lowering into exactly one `NetProperty`; the "Checks:" line is rendered from the `NetProperty` the worker hashed, never from stored text or parameters. Every template and preset has a lowering golden test. A failed precondition is Unknown "property cannot be checked" with a named line, never a different or smaller property.
  - Strings a slice cannot check yet are never interpreted: slice 0 keeps every predicate and `[final]` string opaque and lowers `final none`; a `[final]` table present in slice 0 is the warning `finalNotChecked`; user properties and templates are Unknown "property cannot be checked" before slice 4. Slice 1 adds the one predicate parser (`model::property`), used only by the final predicate until slice 4.
  - Every Proved carries its technique and marking count to the UI, and the drop places of a `NoOverflowPlace` certificate, so the vacuity guard (slice 4: no dead transitions next to user properties) and the reader can see how much was covered.

  (ADR 0018, ADR 0019, net-semantics §9.6, decisions D-05, D-20, D-25)

  Why: a Proved for a question the user did not ask is as wrong as a wrong Proved.

## FMT – Project files

- **FMT-1 must** Every project file carries its own format version (`format`).
  - Every change to the format bumps the version and ships in the same PR with a pure migration `vN → vN+1`, plus a fixture project of the old version and a test that it still loads.
  - Fixtures of released versions are never edited.
  - A project from a newer format version is refused with a message. An element file with a kind the app does not know does not load: it is reported, kept byte for byte and never written, and the scopes it could change are blocked (`docs/specs/file-format.md` §10.5).
  - Unknown fields are never dropped silently: they are kept verbatim and reported. Strings a slice does not interpret yet (predicates and `[final]` in slice 0) are written back verbatim.

  (ADR 0001, ADR 0020, raubritter API-5, raubritter API-8)

  Why: project files outlive every release, and a migration that is not tested on an old project is how a user's model disappears after an update.
- **FMT-2 must** Never lose a user's file.
  - Save writes each changed file atomically: a temp file `.pn-<8 random lowercase hex>.tmp` in the same directory, `sync_all`, rename, then fsync the directory. `std::fs::write` is disallowed [auto].
  - Every gesture is appended to the recovery journal in the app data folder. A window that cannot hold the journal lock opens the project read-only; journals moved aside are all kept.
  - The loader reports dangling references and name clashes as problems instead of failing; one bad element file never stops the project from opening.
  - A file that changed on disk while open is never silently overwritten (UX CNV-5).
  - Code deletes or moves user files only as the direct result of a user command. The app's own leftover temp files, matching exactly `.pn-<8 hex>.tmp`, are not user files and are removed at open.

  ```rust
  // ✅ crates/format: the only writer for project files
  fn write_atomic(path: &Path, bytes: &[u8]) -> io::Result<()> {
      let dir = path.parent().expect("project files live in a directory");
      let temp = dir.join(format!(".pn-{:08x}.tmp", random_u32())); // same directory: rename stays on one file system
      let mut file = File::create(&temp)?;
      file.write_all(bytes)?;
      file.sync_all()?;
      fs::rename(&temp, path)?; // Windows: retried on a sharing violation (file-format §11.4)
      File::open(dir)?.sync_all()
  }
  // ❌ a crash mid-write leaves a truncated element file
  fs::write(path, bytes)?;
  ```
  (ADR 0001, ADR 0006, ADR 0020)

  Why: the project is the user's work, often their only copy outside git, and every write path is a chance to truncate it.
- **FMT-3 must** IDs are slugs, created once with a collision suffix (`order-api`, `order-api-2`). They never change on rename, and references between files use them.
  - Element, relationship, view and property IDs are lowercase, start with a letter, do not end in `-`, have at most 48 characters and are never a Windows device name. Names inside a behavior model keep their case, contain no `__` and do not end in `-`. None is `and`, `or` or `not`. Display names keep any case.
  - The slug generator never reissues an ID that anything still references.
  - The writer is canonical: deterministic order (sorted keys, `BTreeMap`, no `HashMap` iteration in output) and explicit serde attributes.
  - Layout goes only into the per-view layout files.
  - Reading and writing an unchanged project produces byte-identical files (TEST-3).

  (ADR 0001, ADR 0020, TigerStyle)

  Why: stable IDs and canonical output keep a git diff limited to the change the user made, and a rename that rewrites IDs touches every file that references the element.

## SEC – Tauri security

- **SEC-1 must** Capabilities are minimal.
  - There is one capability file per window, with only the permissions that window uses. Commands are registered through the app manifest.
  - No remote URLs, and no `fs` or `shell` plugin permissions for the WebView.
  - All file access happens in Rust commands, inside the open project directory, plus the app data folder for the journal and log. Paths are canonicalized and must stay inside that root, including through symlinks.

  (Tauri)

  Why: the WebView is the lower-trust side, so a bug or injected script in the UI must not reach files outside the project.
- **SEC-2 must** Data that crosses the WebView boundary is untrusted in both directions.
  - Every command validates its arguments before use: IDs are parsed into newtypes and looked up, numbers and lengths stay within LIM-2, paths follow SEC-1. Invalid input is rejected, not clamped.
  - The UI renders text from project files only as text, never through `innerHTML` or `dangerouslySetInnerHTML` [auto], because projects can come from other people's repositories.

  (Tauri, raubritter SEC-1)

  Why: a command is callable with any payload from the WebView, and a description field in a cloned repository is attacker-controlled text.
- **SEC-3 must [auto]** Never shell out with user or model input. `std::process::Command` is disallowed outside test harnesses (the TAPAAL runner uses `#[expect(…, reason)]`), and `tauri-plugin-shell` is not used.

## IPC – Commands, jobs and bindings

- **IPC-1 must** Commands are thin: deserialize, validate (SEC-2), call `engine`, map the error (SAFE-3). `app/src-tauri` contains no domain logic.
  - Checks and scans run as `engine` jobs. A job returns its job ID at once, reports progress and results over a `Channel`, and can be cancelled. Cancelling a check ends it as Unknown ("cancelled").
  - One user gesture is one command, one journal entry and one undo step in `engine`.

  ```rust
  // ✅ app/src-tauri
  #[tauri::command]
  fn start_check(
      app: State<'_, AppState>,
      property: PropertyId, // newtype: deserializing validates the slug (SEC-2)
      events: Channel<CheckEvent>,
  ) -> Result<JobId, CommandError> {
      app.engine.start_check(&property, ChannelSink::new(events)).map_err(CommandError::from)
  }
  // ❌ a command that explores the net itself and blocks until the check ends
  ```
  (ADR 0004, ADR 0001, Tauri, raubritter R-14)

  Why: long work on the IPC path freezes the editor, and a gesture split over several commands cannot be undone or recovered as one unit.
- **IPC-2 must** IPC types are generated by ts-rs and committed. Nobody writes or edits them by hand, and `check` fails when the regenerated bindings differ [auto].
  - `u64` and `i64` fields are exported as `number` and asserted ≤ 2^53 − 1 where they are built.
  - Components never call `invoke` and never create a `Channel` themselves; one `ipc/` module wraps both.

  ```rust
  #[derive(Serialize, TS)]
  #[ts(export)]
  pub struct CheckProgress {
      #[ts(type = "number")] // below 2^53, asserted where it is built
      pub markings_explored: u64,
  }
  ```
  ```ts
  // ✅ import { startCheck } from '@/ipc/checks';
  // ❌ await invoke('start_check', { property }) inside a component
  ```
  (raubritter STR-7)

  Why: a JS `number` silently rounds above 2^53, and a hand-written type drifts from Rust without any compiler error.

## NAM, API – Naming and API design

- **NAM-1 must** Domain concepts use the exact terms from `GLOSSARY.md` and never its _Avoid_ words. This applies to Rust, TS, file names, and log and error messages.
  - Exceptions are third-party types (React Flow's `Node` and `Edge`, only inside the canvas adapter that maps elements and relationships to them) and technical meanings (Rust's `Result`, `assert!`, P-invariant).
  - A `Job` in `engine` is the technical unit that runs a check or scan; it never names a check.
  - The time and memory a check may use is its `Budget`, never a `limit` or `bound`.

  ```rust
  // ✅
  struct Relationship { source: ElementId, target: ElementId }
  budget.markings_max
  // ❌
  struct Edge { … }              // Relationship
  struct CheckResult { status }  // Verdict
  struct Trace(Vec<Step>)        // Counterexample
  fn lint_model(…)               // a Scan applies Rules
  states_explored                // Markings, not states, in a Petri net
  ```
  (GLOSSARY, raubritter NAM-2)

  Why: a second word for one concept splits code, docs and UI, and search finds only half of the places.
- **NAM-2 should** Rust names follow Google and the Rust API Guidelines:
  - acronyms as words (`TomlError`, `PnmlExport`)
  - `as_`/`to_`/`into_` conversions
  - getters without `get_`
  - `new`/`try_new`/`from_*` constructors
  - no abbreviations (short names only for closure arguments and indexes)
  - no weasel words (`Manager`, `Service`, `Helper`, `Util`)
  - units last (`timeout_ms`, `size_bytes`)

  Imports and modules: one module per `use`, because rustfmt cannot enforce `imports_granularity` on stable, and free functions are called through their module (`mem::take`). Glob imports are **[auto]**.

  TS: kebab-case file names, `PascalCase` components, `useX` hooks, `handleX`/`onX`, no default exports, no barrel files.

  (Google, API C-CASE, API C-CONV, API C-GETTER, MS M-WEASEL-WORDS, raubritter NAM-1, NAM-5, STR-6, STR-9)
- **API-1 must** (core crates; app code should) Interfaces cannot be misused by accident:
  - An enum instead of a `bool` for non-obvious parameters.
  - An options struct with `Default`, or newtypes, when two arguments of the same type can be swapped.
  - Accept `&str`, `&[T]` and `Option<&T>`, and prefer named fields over tuples.
  - Closed sets are enums with exhaustive `match`.
  - No `Rc`, `Arc`, `RefCell` or deep `.clone()` without a reason in a comment.

  ```rust
  // ✅
  explore(&net, &Budget { markings_max: 1_000_000, ..Budget::default() }, &cancel)
  // ❌ which number is which, and what does `true` mean?
  explore(&net, 1_000_000, 512, true)
  ```
  (Google, API C-CUSTOM-TYPE, API C-NEWTYPE, TigerStyle)

  Why: a swapped `u64` or a meaningless `true` compiles and runs a check with the wrong budget.

## TEST – Tests

- **TEST-1 must** New core logic has tests, and a bug fix comes with a test that failed before the fix.
  - Tests check behavior, not restated constants or a mirror of the implementation.
  - No test depends on wall-clock time, sleeps or unseeded randomness. Budgets in tests are marking counts, and time reaches a budget through a parameter.
  - UI: logic runs in Vitest, and canvas components run in Vitest browser mode with only the IPC boundary mocked (`mockIPC`). Playwright is for the UX capture in `UX_STANDARDS.md`.

  (raubritter TEST-1, raubritter TEST-3, raubritter TEST-7, raubritter TEST-8, MS M-TAUTOLOGICAL-TESTS)

  Why: a timing-dependent test fails on a slow CI runner and teaches everyone to re-run red builds.
- **TEST-2 must** `verify` has property tests (proptest) over generated valid and invalid nets. They show that:
  - both explorers agree
  - every accepted certificate holds and every mutated certificate is rejected
  - every counterexample replays to its violation
  - a budget too small for the net yields Unknown, never Proved

  Changes to `verify` keep the TAPAAL differential corpus green in CI, and every bug in `verify` adds its net to the corpus. proptest regression files are committed. (TigerStyle, ADR 0008)

  Why: the main explorer, the second explorer and TAPAAL fail differently, so their agreement is the evidence that a verdict is not a coincidence.
- **TEST-3 must** The canonical TOML writer has insta snapshot tests. A changed snapshot is a format change and needs FMT-1.
  - Each released format version has a fixture project that loads, and reading and writing it is byte-identical (FMT-3).
  - The file parser is fuzzed nightly (cargo-fuzz, not a merge gate), and every crash found becomes a regression test.

  (ADR 0001, TigerStyle)

## TS, R, UI – TypeScript, React and accessibility

- **TS-1 must** tsc runs with:
  - `strict`
  - `noUncheckedIndexedAccess`
  - `verbatimModuleSyntax`
  - `erasableSyntaxOnly`

  Together with the Oxlint config, these ban `any`, `@ts-ignore`, `enum`, floating promises and `console.*` [auto]. In review:
  - Data from outside the generated IPC types (clipboard, drag-and-drop, `localStorage`, `postMessage`) is `unknown` and narrowed before use, never cast with `as`.
  - A `switch` over a union (verdict, IPC error `kind`, element kind) ends with `assertNever`.
  - A `catch` handles the error, rethrows it, or says why ignoring it is safe.

  ```ts
  // ✅
  switch (verdict.kind) {
    case 'Proved': return <ProvedBadge evidence={verdict.evidence} />;
    case 'Disproved': return <ReplayButton counterexample={verdict.counterexample} />;
    case 'Unknown': return <UnknownReason reason={verdict.reason} />;
    default: return assertNever(verdict);
  }
  // ❌
  const kind = JSON.parse(event.dataTransfer.getData('application/json')) as ElementKind;
  ```
  (raubritter TS-1, TS-2, TS-3, TS-4, TS-6, TS-13)

  Why: a new verdict reason or error kind must break the build at every place that shows it, not fall through silently.
- **R-1 must** Every piece of state has exactly one home: the core owns the model, and the Zustand store holds a read projection plus view state.
  - Components read the store through narrow selectors, with `useShallow` when a selector builds an object or array.
  - The store changes only from core responses, Channel events and view actions; model edits are IPC commands.
  - Zustand stays on v4, the version React Flow 12 depends on.

  | Kind | Home | Examples |
  |---|---|---|
  | Model and history | Rust core (`engine`) | elements, relationships, behavior models, properties, layout, undo history, unsaved changes |
  | Results | Rust core | verdicts (in-memory cache, ADR 0005), findings, job progress |
  | Read projection | Zustand store, replaced from core responses and Channel events | elements and relationships of the open view, shown verdicts |
  | Shared view state | Zustand store | viewport, selection, open panels, replay step, drag position before drop |
  | Component-local state | `useState` | open menu, input text before it is committed |
  | Derived values | nowhere: compute in render or in a selector | number of Unknown verdicts, whether Save is enabled |

  ```tsx
  // ✅
  const element = useViewStore((s) => s.elementsById[elementId]);
  const selectedNames = useViewStore(useShallow((s) => s.selection.map((id) => s.elementsById[id]?.name)));
  // ❌ re-renders on every store change
  const store = useViewStore();
  // ❌ edits the model in the UI; the core, the journal and undo never hear about it
  useViewStore.setState((s) => ({ elements: [...s.elements, element] }));
  ```
  (raubritter R-1, raubritter R-2, raubritter R-13, ADR 0004)

  Why: two homes for the model are two truths, and an edit the core never saw is missing from Save, the journal and undo.
- **R-2 must** `useEffect` only synchronizes with an external system: a Tauri Channel subscription, the ELK worker, DOM APIs. It always has a cleanup.
  - Derived values are computed during render.
  - A reset when a prop changes uses `key`.
  - A reaction to a user action goes in the event handler.
  - External stores are read with `useSyncExternalStore`.

  ```tsx
  // ✅ owns the layout worker for the component's lifetime
  useEffect(() => {
    const worker = new Worker(new URL('./elk-worker.ts', import.meta.url), { type: 'module' });
    layoutWorkerRef.current = worker;
    return () => worker.terminate();
  }, []);
  // ❌ derived value
  useEffect(() => setUnknownCount(verdicts.filter(isUnknown).length), [verdicts]);
  // ❌ reaction to a user action
  useEffect(() => { if (saveRequested) void saveProject(); }, [saveRequested]);
  ```
  (raubritter R-2, raubritter R-3, raubritter R-18)
- **R-3 must** Components are defined at module level, render is pure, and `<StrictMode>` stays on. Keys come from stable IDs (element and relationship slugs), never from array indexes or values created during render. (raubritter R-8, R-10, R-20)

  Why: a component defined inside another remounts on every render, and an index key moves focus and selection to the wrong element after a delete.
- **R-4 must** The canvas stays fast:
  - `nodeTypes` and `edgeTypes` are module-level constants.
  - Custom nodes and edges are `memo` components that read only their own data.
  - No component outside the canvas subscribes to the full node or edge array.
  - elkjs runs only in its Web Worker, and only on explicit auto-layout or for elements without a position.
  - Dragging updates view state and sends one command on drop (IPC-1).
  - Further tuning needs a before/after measurement with the `large-model` seed.

  ```tsx
  // ✅ stable identity
  const ElementNode = memo(function ElementNode({ data }: NodeProps<ElementNodeType>) { … });
  const nodeTypes = { element: ElementNode } satisfies NodeTypes;
  // ❌ new object every render: React Flow re-creates every node
  <ReactFlow nodeTypes={{ element: ElementNode }} … />
  ```
  (React Flow, raubritter PERF-5)

  Why: at 300 elements per view, one whole-canvas re-render per mouse move or a layout run on the main thread makes the editor unusable.
- **R-5 should** A component with more than about 5 boolean props is split by composition (`children`, sub-components). UI components are restyled through `variant` and `size`, not through `className` overrides. Props that differ by kind are a discriminated union rendered with an exhaustive switch, and Context holds only rarely changing values. (raubritter R-11, R-12, R-16, R-23)
- **UI-1 must** The UI is accessible:
  - Clickable things are `<button>` or `<a>`, and every input has a label.
  - `<html lang="en">` is set and focus is visible.
  - Every canvas action has a keyboard path and a command (UX A11Y-3).
  - A verdict is text plus an icon and is announced with `role="status"`, never shown by color alone (UX VRD-1).
  - Dialogs, menus, tabs and comboboxes come from shadcn/ui on Base UI.

  (raubritter UI-1, UI-2, UI-3, UI-4, UX_STANDARDS)

  Why: a verdict shown only as a green or red border is unreadable for common color vision deficiencies and invisible to screen readers.
