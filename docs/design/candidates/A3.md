# A3 — C: UI-owned model, Rust compute service

Author: software architect. Style: UI-owned model (client state as truth) with a stateless-ish Rust compute service holding a replica.

> The editable model lives in the React/Zustand store with undo via immer patches; Rust keeps a replica fed by document syncs and does what must be trusted: files, journal, lowering, hashing, checks and scans.


## 1. Idea
The editable model lives where the interaction happens: in the Zustand store, as plain documents (one per element file plus layout per view), edited with immer and undone with immer patches. Rust is a compute and persistence service. It keeps a replica of the documents, fed after each gesture, and does everything that must be trusted or fast: TOML files, recovery journal, lowering, hashing, checks, replay and scan. Style: **UI-owned model with a Rust compute service** (the client is the system of record for editing, the server is the system of record for evidence).

## 2. Structure
```
app/ui
  domain/   generated ts-rs document types + edit operations (immer) + slug rules + validation
  store/    Zustand: docs, undo/redo (immer patches), dirty set, verdicts, findings, replay
  canvas/   React Flow renderers, elkjs worker        panels/  netview/
  bridge/   typed invoke wrappers; syncDocs after each gesture
        │ invoke: open, sync_docs, save, start_check(Channel), cancel_check, run_scan ; event: disk_changed
        ▼
app/src-tauri ─▶ crates/engine (Replica, lowering, hashing, JobRegistry, VerdictCache; no undo)
                  ├─▶ format (TOML, journal codec)  ├─▶ scan → model  └─▶ verify → nothing
```
Dependency rule: `ui/domain` imports only generated types. `canvas` and `panels` read from `store` and never call `bridge` directly. Crate edges are as in ADR 0004, but `engine` keeps no history. `model` is the canonical document schema and validator, and the source of the ts-rs types.

## 3. Core types and seams
```rust
pub struct Replica { rev: u64, docs: HashMap<DocPath, Doc>, model: Arc<Model> }   // Model rebuilt incrementally from docs
pub enum Doc { Element(ElementDoc), Layout(LayoutDoc) }
pub struct SyncResult { rev: u64, problems: Vec<ModelProblem>, stale: Vec<PropertyId>, cancelled: Vec<JobId> }
pub fn sync_docs(r: &mut Replica, rev: u64, upsert: Vec<(DocPath, Doc)>, remove: Vec<DocPath>) -> SyncResult; // also journals
pub fn start_check(r: &Replica, p: PropertyId, b: Budget, out: impl Fn(CheckEvent)) -> JobId;
pub fn save(r: &Replica, disk: &dyn Disk) -> Result<SaveReport, SaveError>;   // writes what differs from disk
// verify: plain Net + Composite, check / explore_simple / replay as in ADR 0004 and 0008
```
```ts
type Docs = { elements: Record<ElementId, ElementDoc>; layouts: Record<ViewId, LayoutDoc> };
type Gesture = (d: Draft<Docs>) => void;                  // immer recipe
type HistoryEntry = { patches: Patch[]; inverse: Patch[]; touched: DocPath[] };
type CheckEvent = { kind: "progress"; markings: number; elapsedMs: number } | { kind: "verdict"; verdict: VerdictDto };
```

## 4. Main flows
- **Open:** `open(path)` reads and migrates files in Rust, reports dangling references, fills the replica and returns all documents (2,000 elements as JSON is a few MB, which is fine once). The store takes them. If a journal exists, Rust returns its documents too and the UI offers to restore them.
- **Edit and undo:** a gesture runs `produceWithPatches` and pushes a `HistoryEntry`, and the canvas updates immediately. `bridge` sends `sync_docs(rev, touched docs)` in order. Rust validates, journals the documents (state-based, idempotent), updates the replica, rehashes affected properties and returns stale and cancelled IDs. Undo applies the inverse patches and syncs again; a verdict cached under the restored hash comes back (ADR 0005). If Rust reports `problems`, the UI shows them and does not roll back.
- **Save:** `save()` writes each replica document that differs from disk atomically (temp file, rename), then clears the journal. The UI clears its dirty set when it receives the `SaveReport`.
- **Check:** `start_check(property, channel)`: Rust lowers from the replica, hashes and looks up the cache, then spawns the named check thread. The main explorer runs, then the second plain-BFS explorer on the unflattened Composite within the same budget (ADR 0008). A Disproved is replayed on the Composite, and a join error gives Unknown "internal error" (ADR 0006). Progress and the verdict stream over the `Channel`. Cancel sets the flag and gives Unknown "cancelled". A sync that changes a running check's hash cancels it in Rust.
- **Replay:** the verdict carries `ReplayStep[]` already mapped to elements and qualified places. The UI overlays highlights on its own documents with no IPC per step, and can show token counts on the net view because it holds the net documents.
- **Scan:** `run_scan()` on the replica returns findings with `NotCheckable`. Suppressions are document data edited in the UI like any other field.
- **File changed on disk:** a `notify` watcher in Rust compares hashes and drops own-save echoes, then emits `disk_changed{paths, docs}`. The UI decides: apply disk documents as a non-undoable reset of those documents, or keep mine. Undo entries that touch those documents are dropped.

## 5. Concurrency and IPC
The Rust side has Tauri threads, `Mutex<Replica>` (a short lock per sync), one named thread per check plus a reaper, and the watcher thread. tokio stays in src-tauri. IPC is a `sync_docs` per gesture, a `Channel<CheckEvent>` per check and a `disk_changed` event. Syncs carry `rev` and are serialized through one promise queue in `bridge`, so Rust sees edits in order. The UI store holds the **whole model** as documents, the undo stack, the dirty set, verdicts keyed by property with their hash, findings, the replay cursor and per-view memoized selectors for React Flow.

## 6. How it grows
- **State machines:** a new document variant, an editor in TS, and a compiler in Rust lowering. Edit rules live in TS.
- **Cross-level composition:** in Rust lowering only.
- **Code import:** Rust produces documents, and the UI merges them as one undoable gesture. Merge logic lands in TS.
- **Code proofs and scan rules:** Rust only, with the UI unaffected beyond panels.
- **CLI:** check, scan and export on files on disk reuse `engine`, but **no editing or scripting** without porting TS domain logic.

What changes most over time: the TS domain layer grows with every notation, while the Rust side grows only with analysis.

## 7. Testing
- `ui/domain`: Vitest and fast-check (gesture then inverse equals identity, slug collisions).
- Contract tests: shared fixture projects are loaded in TS and Rust, and both produce byte-identical canonical documents and the same validation problems.
- Rust: `engine` replica, lowering, hash and job tests with `MemDisk`; `verify` corpus against TAPAAL; `format` round trip and migrations.
- E2E: WebdriverIO carries more weight than in the other designs, because the sync ordering between TS and Rust is a real seam.

## 8. Trade-offs
- **Strengths:** the fastest canvas feel (no round trip on gestures) and the quickest slices 0 and 1. Undo is library-grade (immer patches). React devtools show the whole model. Rust stays focused on what must be trusted.
- **Weaknesses:** two domain implementations (TS edits, Rust validates and lowers) that will drift, and contract tests are a cost forever. The model lives in a webview, so a JS exception can corrupt it (journal and Rust validation limit the damage). The CLI cannot edit. A 2,000-element store needs selector discipline to keep re-renders bounded.
- **Cost (my estimate):** slice 0 in about 4–5 weeks, slices 0–5 in about 7 months, because each notation is built twice.
- **Main risk:** silent TS/Rust divergence producing a lowered net that differs from what the user sees. It cannot cause a wrong Proved about the replica, but it can prove the wrong model.

## 9. ADR conflicts
**Changes ADR 0004.** Undo history leaves `engine` and moves to `app/ui`. `engine` holds a replica, not the authoritative model, and the promise that "a CLI can sit on engine" narrows to check, scan and export. The reason would be interaction latency and UI iteration speed. ADR 0001 and 0005 hold, and the recovery journal stays in Rust. Adopting this needs a superseding ADR.


## Reviews

### By the senior backend developer: 3/10, reject

- Strengths: Gestures have no IPC round trip, and immer patches give working undo quickly.; Trust-critical work (lowering, hashing, checking, replay, journal, Save) stays in Rust, and the replica carries a rev.; The verdict carries ReplayStep[] already mapped through provenance, so the UI steps through it locally.; It is honest about the cost: two domain implementations, a CLI that cannot edit, and a superseding ADR.
- Risks: Proving the wrong model: if a sync_docs call fails, is rejected or arrives late, the Rust replica differs from what the canvas shows, and a Proved about the replica is displayed against a different model. For the user that is a wrong Proved. Every verdict would need the replica rev, and the UI would need to compare it with its own rev before showing it as current.; On 'problems' the UI 'does not roll back', so the UI and the trusted replica can hold models that Rust considers invalid. What exactly is checked then becomes ambiguous.; Every notation (state machines in slice 2, later code import merges) is built twice, once in TS and once in Rust, and contract tests become a permanent cost.; A JS exception can corrupt the authoritative model inside the webview. Rust validation only limits the damage after the fact.; Undo's 'verdict comes back' still needs a sync round trip, so the zero-latency advantage only holds for the canvas, not for verdict state.; A headless CLI, agents and code import cannot edit without porting TS domain logic, which hurts the growth path to code import and code proofs.
- ADR fit: Supersedes ADR 0004 (undo leaves engine, engine holds a replica, the CLI promise narrows). It keeps 0001's journal in Rust and keeps 0005, 0006 and 0008 in the check path, but 0006's 'panic while editing ends the app' no longer covers the real editing path (JS). The reason given, interaction latency, has not been measured yet (that is the E4 spike), so the ADR change is premature.
- Worth keeping: If the E4 spike shows round-trip latency is a problem, use optimistic local application of a gesture in the UI, confirmed by Rust's rev, instead of moving the model.; Contract fixtures loaded by both TS and Rust to keep generated types and validation honest.; Rust rejects invalid documents at the trust boundary and reports problems instead of crashing.

### By the senior frontend developer: 3/10, reject

- Strengths: Zero round trip per gesture: drag, multi-select and undo are all local, and immer patches give library-grade undo quickly.; Rust still owns everything trusted (TOML, journal, lowering, hashing, checks, scan), and progress plus verdicts stream over a per-check Channel.; Being honest about the cost (each notation built twice) and the ADR 0004 change is useful input for the decision.
- Risks: The checked model is the Rust replica, but the user looks at the TS documents. A lost or mis-ordered sync_docs, or a TS/Rust rule divergence, means a Proved is shown next to a canvas that is not the model that was proved. For a tool where 'a wrong Proved must never happen', that is the worst kind of bug: silent and plausible.; Two domain implementations (TS edits and slug/collision rules, Rust validation and lowering) for every notation. State machines (slice 2), user properties (slice 4) and code import all land twice, and contract tests are a permanent tax for one developer.; Holding the whole model (about 2,000 elements) in a webview store means a JS exception mid-recipe can corrupt the system of record. ADR 0006's fail-fast policy has no clean equivalent here, and the design does not define one.; The latency argument is weak in practice. Discrete gestures over Tauri IPC cost a few ms, and drag is local in every design anyway. The win is real only for drag, and A1/B1 already cover drag.; On external changes the UI decides and the undo entries are dropped, which repeats A1's UX loss.; The CLI cannot edit, and code import or rename-across-files refactors would need to be written in TS or ported.
- ADR fit: Changes ADR 0004 (undo history leaves engine, engine becomes a replica) and needs a superseding ADR. Weakens ADR 0006 in practice, because editing errors become JS exceptions with no fail-stop policy stated. Keeps ADR 0001/0005/0008. The reason given (interaction latency) is not backed by a measurement, and the round-trip cost can be tested in the React Flow spike before giving up the ADR.
- Worth keeping: CheckEvent progress (markings, elapsedMs) streamed over a per-check Channel for a live progress line in the verdict panel; Replay token counts on the net view: the UI needs the element's net documents (read-only) to render markings during replay, so project them for the net view in slice 1; Contract fixtures loaded on both sides as a guard for ts-rs types, which only guarantee shape
