# B3 — Design C: UI-owned document, Rust as stateless compute and storage

Author: senior backend developer. Style: UI-owned model with Rust compute service (thick client + service layer, language-server shape).

> The Zustand store owns the model document, undo history and edit validation. Rust is a stateless set of services (load, journal, save, lower/key/check, scan) that receives the data it needs per request. It keeps only the job registry, verdict cache and watcher. Changes ADR 0004.


## 1. Idea
The React side owns the model document: a Zustand store with immer patches holds the model, the undo and redo stacks, selection, dirty tracking and edit validation. Rust is a set of request/response services that receive the data they need with each request: storage (load, journal append, Save), compute (lower, key, check, replay) and scan. The only long-lived Rust state is the job registry, the verdict cache and the watcher.
**Style:** UI-owned model with a Rust compute service (thick client plus service layer), shaped like an editor talking to a language server.

## 2. Structure
```
app/ui  [ doc store + history + validation ] ──ScopeInput / EntityImage──> app/src-tauri (stateless commands)
   ^                                                              │
   └──── Channel<CheckEvent>, event "disk-changed" <──────────────┴──> engine ──> model, format, verify, scan
```
- `model`: serde DTO types (`#[derive(TS)]`), `validate`, slug-ID rules. The canonical definitions of the domain rules.
- `format`: TOML directory, migrations, journal codec (the journal is written by Rust, fed by the UI).
- `verify`, `scan`: as in ADR 0004.
- `engine`: `lower(&ScopeInput)`, `check_key`, `replay_unflattened`, `JobRegistry`, `VerdictCache` (LRU), watcher. **No session and no undo.**
- `app/src-tauri`: stateless commands plus `Mutex<JobRegistry>`, `Mutex<VerdictCache>` and the watcher handle.
- `app/ui`: `doc/` (store, gesture actions, inverse patches), `doc/rules.ts` (a TS copy of the validation and ID rules), `history/`, `canvas/`, `checks/`, `scan/`, `ipc/`, `layout.worker.ts`.
Rule: the UI never computes a net, key or verdict; Rust never holds the model between calls (except the watcher's last-seen hashes).

## 3. Core types and seams
```ts
type ModelDoc = { version: number; elements: Record<ElementId, Element>; relationships: Record<RelationshipId, Relationship>;
                  layouts: Record<ViewId, Layout>; suppressions: Suppression[] };
type Gesture = { id: string; label: string; patches: Patch[]; inverse: Patch[]; touched: EntityKey[] };
type ScopeInput = { scope: ElementId; children: Element[]; relationships: Relationship[]; properties: Property[] }; // ≤ 300 elements
// IPC (hand-written wrappers over ts-rs types)
loadProject(path): Promise<{ doc: ModelDoc; report: LoadReport; restore?: JournalOffer }>;
journalAppend(project: ProjectId, gestureId: string, after: EntityImage[]): Promise<void>; // serialized through one promise queue
saveProject(project: ProjectId, changed: EntityImage[], deleted: EntityKey[]): Promise<SaveReport>;
currentKeys(input: ScopeInput): Promise<Record<PropertyId, CheckKey>>; // also cancels running checks of this scope whose key vanished
runChecks(input: ScopeInput, onEvent: Channel<CheckEvent>): Promise<void>;  cancelCheck(key: CheckKey): Promise<void>;
runScan(doc: ModelDoc): Promise<FindingDto[]>;
```
```rust
pub fn lower(input: &ScopeInput) -> Result<Lowered, LowerError>;           // validates input first: the UI is not trusted
pub fn replay_unflattened(input: &ScopeInput, cx: &Counterexample) -> Result<(), ReplayError>;
pub struct JobRegistry { running: HashMap<CheckKey, RunningCheck>, by_scope: HashMap<ElementId, HashSet<CheckKey>>, .. }
impl JobRegistry { pub fn submit(&mut self, key: CheckKey, l: Lowered, p: Property, b: Budget, sink: Box<dyn EventSink>); pub fn retain_scope(&mut self, s: ElementId, keep: &HashSet<CheckKey>); }
```
`verify` seams unchanged: `check`, `explore_simple`, `replay_net`, `Budget`.

## 4. Main flows
- **Open project:** Rust loads and validates, then returns the whole `ModelDoc` (2,000 elements ≈ 1-2 MB JSON; use raw `ipc::Response` if it exceeds ~50 ms) plus a restore offer from the journal. The UI calls `runChecks` for every scope with properties (ADR 0005).
- **Edit and undo:** a store action produces patches and inverse patches with no IPC. The gesture is pushed on the history, and `journalAppend` sends the after-images through an ordered queue. Then a debounced (100 ms) `currentKeys(scope)` marks stale verdicts and lets Rust cancel checks whose key vanished. Undo applies the inverse patches, journals them, and calls `currentKeys`; cached verdicts return.
- **Save:** the UI sends the dirty entity images; Rust journals `SaveBegin`, writes temp + fsync + rename per file, journals `SaveDone` and resets the journal; the UI clears `dirty`.
- **Run a check:** the UI builds the `ScopeInput`; Rust validates, lowers, keys and looks up the cache, then submits. The worker pipeline is as in Design A: named thread, main explorer, `explore_simple` on the shared deadline, flat and unflattened replay, monitor join -> Unknown "internal error" on panic. Verdicts stream on the Channel; the UI keeps a verdict only as current if its key equals the scope's current key.
- **Replay:** steps in model terms in the Disproved verdict; the UI steps locally.
- **Scan:** the UI sends the `ModelDoc`; Rust returns the findings with the doc's structural hash.
- **File changed on disk:** the Rust watcher parses the changed files, drops our own writes by hash, and emits `disk-changed` with entity images. The UI store merges clean entities as one undoable gesture and shows a conflict for dirty ones.

## 5. Concurrency and IPC
- JS: single-threaded store; elkjs in a Web Worker; one promise queue for journal and Save so their order matches the gesture order.
- Rust: Tauri async commands; check workers and monitors as in A; the watcher thread; two short-held mutexes (registry, cache). There is no model lock because there is no model.
- IPC per gesture: one `journalAppend` (small) and one debounced `currentKeys` (the scope, ≤ 300 elements, roughly 50-150 KB JSON; measure).
- UI store: the whole `ModelDoc`, history, selection, `currentKeys`, verdicts, findings, replay cursor. This is the largest store of the three designs.

## 6. How it grows
- **State machines:** an editor in TS plus compilation in Rust's `lower`; the TS validation rules grow too.
- **Cross-level composition:** `ScopeInput` grows from one view to a subtree; at depth it approaches sending the whole model per check, and you will want a Rust-side mirror, which is Design A by the back door.
- **Code import:** Rust returns entity images; the UI applies them as one reviewable gesture.
- **Code proofs:** external runners in Rust, keyed by input hash. **More scan rules:** `impl Rule`, no UI change.
- **CLI:** works well, because the CLI never edits: load, lower, check and scan are all Rust. The edit logic in TS is not reusable by a CLI or by a later "rename across files" refactor.
- **Option to remove the duplication:** compile `model` (validate, slug IDs) to WASM and call it from the store (stack.md §7.3). This adds a second build target.

## 7. Testing
- UI (now a large share of the domain tests): Vitest plus fast-check on the store, checking that applying a gesture's patches and then its inverse is the identity, and that the ID and collision rules hold. `mockIPC` for the command wrappers.
- Contract tests: TS fixtures of `ModelDoc`/`ScopeInput` are checked into the repo and must pass `model::validate` in `cargo test`; Rust-rendered fixtures must load in Vitest. ts-rs guarantees only the shape, so these guard the semantics.
- Rust: `verify` and `format` as in A; `lower` on `ScopeInput` fixtures; registry cancellation by scope.
- Crash test: WebdriverIO kills the app after N gestures, then restore. The journal path crosses IPC, so it needs E2E.

## 8. Trade-offs
- **Strengths:** the snappiest editing (drag, multi-select and undo are local, with no round trip); the Rust side is small and stateless, which keeps reasoning simple; it fits React Flow and Zustand idioms; the fastest route to a first demo.
- **Weaknesses:** domain rules in two languages (slug IDs, collision suffix, port binding validity, capacity > 0) that drift, and the checker then proves a model the UI built wrongly. Rust re-validates every input, so a wrong model is rejected rather than proved, but the user sees a late error. Stale marking and cancellation need scope data sent after each edit. A renderer crash loses the gesture whose `journalAppend` had not reached Rust, which ADR 0001's "last gesture" allows. A JS exception in a store action can leave a half-applied gesture instead of failing fast.
- **Cost for one developer:** slice 0 is about 5-6 weeks, the cheapest start. Slices 3-5 cost the most, because every model rule lands twice.
- **Main risk:** the duplicated domain logic diverges, and cross-level composition forces a Rust-side model anyway.

## 9. ADR conflicts
- **Changes ADR 0004:** the undo history moves from `engine` to `app/ui`, and `engine` becomes stateless compute plus the job registry and verdict cache. Reason: to keep the whole gesture path in the UI for latency and a simpler Rust side.
- **Adjusts ADR 0006 in spirit:** an editing error is now a JS exception, not a main-thread panic. The equivalent policy is fail-stop: on an uncaught store error, flush the journal and reload from disk plus journal; never continue on a possibly half-applied document.
- ADRs 0001, 0005 and 0008 hold; it shares Design A's clarification that unflattened replay lives in `engine`.


## Reviews

### By the software architect: 3/10, reject

- Strengths: Zero-latency editing: drag, multi-select and undo stay local.; The Rust side stays small and stateless, apart from the job registry and verdict cache.; Rust re-validates every ScopeInput as untrusted input. Shipping and checking each fixture in both languages is the right mitigation if this shape were chosen.; It honestly names its own failure mode: cross-level composition forces a Rust-side mirror ('Design A by the back door').; Journal entries are entity after-images written by Rust, not UI patch paths, which is better than C2.
- Risks: Correctness: the TS store assembles the ScopeInput, which decides which children and relationships go into the composed net. A UI bug that drops a sibling or a binding passes Rust validation, because each piece is valid, and yields a Proved for a composition that is not the model. Rust cannot detect this without owning the model. That is a wrong Proved with no structural defense.; Domain rules exist twice (slug IDs, collision suffix, binding validity, capacity). They will drift, and every slice from 2 to 5 pays the duplication tax.; Code import, a 'rename across files' refactoring, a CLI with editing, and agent edits all have no home in Rust. That blocks the growth path toward code import and conformance.; The latency it optimizes for is unmeasured (a few ms per IPC round trip), and B1 and C1 already keep drag local until the gesture ends. It changes an ADR to fix a problem that is not known to exist.; A renderer crash loses a gesture whose journalAppend was in flight. A JS exception can leave a half-applied document, so the crash policy has to be reinvented in the UI.; Stale marking needs scope data re-sent after every edit, at about 50-150 KB per debounced currentKeys call.
- ADR fit: Changes ADR 0004: undo leaves engine and engine loses its session. The stated reason (latency, a simpler Rust side) is a preference without a measured driver, so it does not meet the bar for superseding an accepted ADR. It bends ADR 0006 into a JS fail-stop policy. ADR 0005 and 0008 hold mechanically, but ADR 0008's spirit (a wrong Proved must never happen) is weakened, because the composition input comes from unverified code. Glossary use is correct.
- Worth keeping: Contract fixtures that cross languages: Rust-rendered fixtures load in Vitest and TS fixtures pass model::validate. Use them for ts-rs DTO semantics in any design.; Lowering validates its input first and treats its caller as untrusted. Keep this even when the caller is engine itself.; Defer the WASM build of model (stack.md 7.3) and keep it documented as the escape hatch if a client-side rule is ever needed.

### By the senior frontend developer: 4/10, reject

- Strengths: The check input is the ScopeInput the UI sends, and Rust re-validates it (the UI is not trusted). The checked model therefore equals what the user sees, and a malformed model is rejected rather than proved. That is safer than A3's replica.; Stateless Rust services are easy to reason about. Only the job registry, verdict cache and watcher hold state.; Snappiest editing and the cheapest path to slice 0.; It is candid that cross-level composition pushes toward a Rust-side mirror ('Design A by the back door'), and it states a fail-stop policy for JS store errors.
- Risks: Domain rules live in two languages (slug IDs, collision suffix, port binding validity, capacity > 0, and later state machine and property rules). The user hits late errors from Rust validation for things the TS editor allowed, and every slice from 2 to 5 doubles that work.; Stale marking needs a debounced (100 ms) currentKeys with 50-150 KB of ScopeInput per edit. That is more IPC per gesture than the Rust-owned designs, and it gives a 100 ms window in which an outdated verdict shows as current. That window is small but conflicts with the slice 0 rule that verdicts disappear on any edit.; runScan sends the whole ModelDoc each time, and slice 3 makes ScopeInput a subtree. Payloads grow with the model, and the design predicts it will need a mirror anyway.; The renderer owns the system of record. A webview crash loses the not-yet-journaled gesture, and a JS exception in a store action can half-apply a gesture. The proposed reload-from-journal is sound but has to be built and tested end to end (WebdriverIO).; The latency gain only matters for drag, which is local in every design. No measurement justifies moving the model.; The CLI and refactors such as rename-across-files cannot reuse the edit logic. The WASM escape hatch adds a second build target.
- ADR fit: Changes ADR 0004 (no session or undo in engine) and adjusts ADR 0006 in spirit, so it needs two ADR changes for a benefit that the React Flow spike can disprove cheaply. Keeps ADR 0001, 0005 and 0008 and the unflattened-replay clarification. Terms are used correctly.
- Worth keeping: lower() validates its input as untrusted even when it comes from engine, as defense in depth for the checker; JobRegistry indexed by scope (retain_scope) so cancellation by scope stays O(scope); Raw ipc::Response for the one-time project load if the JSON exceeds about 50 ms; Fail-stop on an uncaught UI store error: flush and reload rather than continue on a possibly half-applied state (also useful for the UI mirror in B1)
