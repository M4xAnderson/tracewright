# Reviews and disposition: Scan rules v1

Author: researcher. Final document: `docs/specs/scan-rules.md`.

## product manager: approve-with-changes

### Must fix
- M1. Interaction from port bindings ignores which way each binding points (§2.4, RUN-SYNC-CYCLE §5, REL-NO-TIMEOUT §6, RS7, NT7). ADR 0002 has no request/reply matching, so a reply is its own sync binding pointing the other way. E5 case 1 does exactly this: `cluster_a/respond -> control_plane/done_a` and `control_plane/ret_a -> api_a/reply` (e5/case1_ebs_bad.toml:8-15), and design.md's `BindPorts{relationship, from, to, binding}` lets a binding point against its relationship. The draft says 'synchronous if any binding is sync'. If the user draws the reply as its own relationship, every request/reply pair becomes a High RUN-SYNC-CYCLE finding ('can wait on each other forever'), the reply relationship gets REL-NO-TIMEOUT entries, and the cycle is also folded into ARCH-CYCLE. That noise lands on exactly the designs v1 targets, and the message would be false. Fix: (a) only bindings whose caller port is in the drawn source set the source's interaction; a reply binding (caller in the target) adds no dependency and is never judged for a timeout; (b) state the modeling convention that one relationship carries a call and its reply; (c) add a test model built from E5 case 1's Container architecture, expecting no RUN-SYNC-CYCLE finding; (d) define what happens when a file stores `interaction` and that relationship also has bindings that disagree. It should be a `validate` problem, never a silent drop (FMT-1: unknown fields are never dropped silently), and binding ports must not discard a stored attribute unless an undoable Command does it.
- M2. Relationship-level `tables` contradicts a decided non-goal. north-star.md Non-goals: 'database tables appear at most as an attribute of Database elements for the scan [decided]'. The draft adds `tables` on relationships (§2.4, §7 steps 5-7, SD3, SD5) and claims 'No ADR is changed' without flagging this. Recommended fix (thinnest slice): cut table-level clearing from v1. Schema-per-service is already expressible because a Database element stands for one logical database or schema (§2.1). Private tables inside one schema become an FP note: suppress as accepted, or draw one Database per schema. If the researcher wants to keep it, mark it as a proposed change to a decided product item for the product owner. Either way, drop the 'tables not stated for' evidence branch or make it consistent.
- M3. Glossary conflicts are not surfaced, although the intro promises that new terms are 'listed in §10 and proposed for the glossary'. §10 lists none. Specifically: (a) Suppression disposition *not real* contradicts GLOSSARY 'Suppression: The user's decision to accept a finding'. The north-star noise guardrail needs it, so propose a glossary amendment explicitly. (b) 'witness cycle' (§3.4 and evidence in §4/§5) uses an Avoid word: 'witness' is on the Avoid list of Evidence and Counterexample, and UX TXT-1 bans Avoid words in UI. Rename it, e.g. 'example cycle' or 'shown cycle'. (c) GLOSSARY defines Not checkable 'for an element', but the draft applies it to relationships, element sets and the whole model ('Not checkable entry'); propose the widened definition. (d) Add a term table for runtime unit, lifted relationship, carrier, remote, entry point, finding key, disposition, identity and 'not stated', each with a proposed glossary line or marked as spec-internal (never shown in UI).
- M4. The handoff from the scan to checks can produce a Proved that reads as more than it is. In §5 Evidence, the panel 'suggests checking deadlock-free' on a sync-cycle finding. E5 case 1 (case1_ebs_timeout) showed that once a timeout exists, deadlock-free and always-reachable are Proved and hide the starvation; only the linear pool-share 'never' predicate stayed Disproved (e5-paper-test.md, Case 1 'Lost', Implication 1). A Proved deadlock-free next to this finding will read as 'the cycle is safe'. Fix: suggest the pool-share predicate template (slice 4 lands before slice 5) next to deadlock-free, and say in the panel that a Proved deadlock-free does not clear this finding. The message also has to depend on the timeouts: 'can wait on each other forever' is false when every step has timeout = yes. Use something like 'can use up each other's request threads; calls then fail by timeout'.
- M5. AC3's expected result contradicts itself ('Two findings… nothing folds into it… so it **does** fold… (2) None other'). These test models become insta golden tests (§9) and the E8 dry run, so they must be exact. By the §4 step 2 rule the result is exactly one finding: Container level, members {a, b}, R = {r1, r2}, plus 'also visible at Component level: {a1, a2, b1}'. Also say explicitly that the in-container a1 ↔ a2 cycle (r3, r4, an independent cause) is absorbed and only reappears as its own Component-level finding after the container cycle is removed. That is acceptable, but should be intended and written down.
- M6. The dependency between rules is undefined and can hide a real cycle. §4 step 3 drops ARCH-CYCLE sets covered by a RUN-SYNC-CYCLE finding, but §3.8 lets RUN-SYNC-CYCLE be disabled (`scan.disabled`). As written, disabling the sync rule could leave a real cycle with no finding from either rule. Fix: step 3 applies only when RUN-SYNC-CYCLE is enabled and produced that finding in the same scan. Add a test model (AC6 with RUN-SYNC-CYCLE disabled: expect F ARCH-CYCLE {a, b}).

### Should fix
- S1. DATA-SHARED-DB contradicts §2.2. §2.2 says 'a quickly drawn design produces Not checkable entries, not findings', yet an unknown `owner` is read as 'each container is its own service'. The result is a finding on the most common C4 microservice drawing, an API container plus a worker sharing their own DB, which is C4's own Microservices example. That is a direct risk to the ≤ 20 % 'not real' guardrail. Recommendation: accessors in different Software Systems, or with different known owners, give a finding; two or more accessor containers of the same Software System with unknown owners give Not checkable 'owner'. Whichever is chosen, make §2.2 and §7 agree.
- S2. REL-SPOF's cut line needs a decision rule tied to evidence, not 'if slice 5 runs long'. problems.md §5 names cycles, sync cycles, timeouts and shared databases, not SPOF, and REL-SPOF needs deployment data (replicas, zones) that the target user may not draw. Proposed rule: REL-SPOF ships in slice 5 only if the E8 dry run on 2 real designs finds at least one real SPOF, and the user could state replicas and zones for most required units without research. Otherwise it moves to 5b or later.
- S3. Make the guardrail computable and add the missing measures (§3.8). Numerator: findings in the current scan suppressed as *not real*. Denominator: all findings in that scan, suppressed included, Not checkable entries and internal errors excluded. Because there are no kind defaults, Not checkable volume is the more likely failure mode. Add the number of Not checkable entries per rule, and how many the user resolved by stating data, to the E8 protocol and the journal. Also add how problems.md's 'at least one finding changes a design in the first month' gets recorded: one journal row per finding that changed a decision.
- S4. 'No findings' must not read as 'clean', which is the scan's version of an overclaiming Proved. The empty state (UX flows.md §4.14, 'No findings. 5 rules ran on 42 elements.') should also show the number of Not checkable entries and disabled rules, and should link to the documented blind spots: flows not started by a Person, external systems never judged, async-only paths, correlated failures, and pool exhaustion without a cycle.
- S5. REL-SPOF wording and FP advice. The message 'every checkout needs it' claims too much, given §8's own note that lifting treats every synchronous call of a reached container as needed. Use 'a flow from Customer reaches it synchronously: Customer → Web App → Orders DB'. The FP advice 'set `replicas` to the number of devices' asks the user to enter false data. Recommend suppressing as *not real* instead (or a client-device kind later).
- S6. Rule isolation and cancellation (§3.5, §3.9). 'its join gives one entry "internal error" for that rule' needs one supervised thread per rule. design.md describes a single `scan-<n>` thread, so either specify a thread per rule or accept that one panic gives 'internal error' for all rules. CODING_STANDARDS says scans run as cancellable engine jobs; say whether a scan can be cancelled and what it then shows.
- S7. Treat `suppressions.toml` and `scan.disabled` as format changes. They need an FMT-1 version bump, a migration, a fixture and a `validate` rule (empty or too-long reason, unknown rule ID). The project-level file is a new part of the layout ADR 0001 describes; say that in Q4 instead of 'changes nothing in ADR 0001'.
- S8. List all deviations from research in §10: REL-NO-TIMEOUT moves from warning (research §6.2) to High, and owner/tables are clearing-only rather than `shared_ok`. Also note that a timeout modeled inside a bound behavior model (E5 case1_ebs_timeout) is not linked to the `timeout` attribute in v1 (research open question 3), which is a known source of Not checkable entries.
- S9. Make §2.1's claim that 'the kind field is part of the format from slice 0' (with Database and Queue) a stated requirement on the format spec and slice 0. Otherwise slice 5 needs a migration, and older builds refuse the new kinds (FMT-1).
- S10. Settle open question 1 in the spec. The glossary already reserves Unknown for verdicts, so adopt 'not stated' as the UI and glossary term for an unknown attribute value now, rather than leaving it open.

### Questions for the user
- The noise guardrail needs a *not real* disposition, but GLOSSARY defines Suppression as 'the user's decision to accept a finding'. May we amend the glossary so a suppression is either accepted or not real, always with a reason?
- Table-level clearing for shared databases goes against your decided non-goal ('tables at most as an attribute of Database elements'). Should we drop it from v1 (schema per service = separate Database elements; private tables are suppressed as accepted), or relax the non-goal?
- When two containers of the same system use one Database and no `owner` is set, should DATA-SHARED-DB report a finding or Not checkable 'owner'? (Recommendation: Not checkable within one system; a finding across systems or between known different owners.)
- Should REL-SPOF depend on the E8 dry run (ship in slice 5 only if E8 finds a real SPOF and replicas and zones can be stated easily), rather than on slice 5 schedule pressure?
- Modeling convention: may one relationship carry both a call and its reply bindings (as in E5 case 1), so replies never look like a synchronous cycle? This also affects how slice 0 lets you bind ports.

## software architect: approve-with-changes

### Must fix
- §4 test AC3 contradicts itself. It says 'Two findings', then says the Component-level set {a1, a2, b1} folds into finding (1), then '(2) None other'. Recomputed under the §4 step 2 rule: there is exactly one finding, at Container level, members {a, b}, R = {r1, r2}, with 'also visible at Component level'. The real problem is that the folding absorbs the a1 <-> a2 cycle (r3, r4). That cycle is an independent cause: it remains if r1 and r2 are removed. So one suppression of the container finding silently hides it too, which breaks the 'one cause, one finding' claim. Fix: after folding C into C', run SCC again at level L on R(C) minus the relationships that carry R(C'), which are exactly the in-parent relationships dropped by lifting. Report any cycle that is left as its own finding at L. Rewrite AC3 to expect two findings: Container {a, b} with Component {a1, a2, b1} folded into it, and Component {a1, a2} through r3 and r4.
- §4 step 3 (drop ARCH-CYCLE sets covered by a RUN-SYNC-CYCLE finding) is under-defined in two ways, and both can give a wrong result. (a) §3.4 defines R(C) only for level graphs. For G_sync it is not said whether asynchronous or unknown carriers of a kept lifted relationship belong to R. If they do not, then a -> b sync plus a -> b async plus b -> a sync gives both a High and a Medium finding for the same pair. (b) The step reads another rule's output, but the spec does not say what happens when RUN-SYNC-CYCLE is disabled (§3.8 scan.disabled), has panicked ('internal error', §3.5), or is suppressed as not real. As written, disabling RUN-SYNC-CYCLE can make a real dependency cycle disappear completely. Fix: compute the synchronous SCCs once as a shared graph fact that does not depend on rule enablement. Drop an ARCH-CYCLE set C only when RUN-SYNC-CYCLE is enabled and has a current finding that is not suppressed as not real and whose members equal {ru(m) : m in C}. Compare member sets, not R sets. State this in §4 and add tests for the disabled case and the suppressed case.
- §7 treats an unknown owner as a known value: 'each container is its own service'. This contradicts §2.2 ('nothing is ever assumed, so a quickly drawn design produces Not checkable entries, not findings') and research §0/§1.2 ('unknown maps to not checkable instead of smell'). The claim that this is C4's default reading is also wrong. I checked https://c4model.com/abstractions/microservices on 2026-11-02: a microservice is 'a group of one or more containers', or is 'promoted' to a software system when a separate team owns it. So the API container and the worker of one service, the most common C4 drawing, produce a finding by default, and that works against the 20 % noise guardrail. Fix: make owner a required attribute for this rule. If the accessor units already known to have different owners form at least 2 identities, report a finding. Otherwise, if 2 or more accessor units exist and an unknown owner could merge them into one identity, report Not checkable 'owner not stated for: a, b'. Otherwise report nothing. Update §2.2 ('Not checkable: never'), §8/§10 and tests SD1, SD3, SD5 and SD6. As drawn, SD1 then becomes NC.
- Relationship-level tables (§2.4, §7 steps 5–7, SD3, SD5) contradicts a [decided] non-goal in north-star.md: 'database tables appear at most as an attribute of Database elements for the scan'. Either drop tables from v1, or get an explicit product-owner change. Dropping is the simpler path. The §2.1 catalog already defines a Database as 'one logical database or schema', so schema-per-service is drawn as separate Database elements, and private-tables-per-service inside one schema is suppressed as accepted with that reason. §10 must list this either way, because right now the spec claims it deviates from nothing that was decided.
- Glossary. The introduction promises that new terms are listed in §10 and proposed for the glossary, but §10 lists none. The spec introduces runtime unit, level graph, lifted relationship, witness cycle, finding key, interaction, entry point, required unit, possibly required unit, refinement attribute and disposition. Two of them change existing glossary meanings. (1) Suppression is 'the user's decision to accept a finding', but the disposition 'not real' is not acceptance. (2) Not checkable is defined 'for an element', but the spec emits it for relationships, element sets and the whole model. Fix: add a glossary section with proposed definitions and amend Suppression and Not checkable. CLAUDE.md requires domain terms to follow GLOSSARY.md exactly.
- §3.9 defines the staleness hash as 'IDs, kinds, parents, relationships, attributes'. It does not say that port bindings and their kinds are included, even though §2.4 derives interaction from them. It also leaves out the enabled rule set. So changing a binding from sync to async, or disabling a rule, can leave old findings displayed as current (GLOSSARY: Current/Stale). Fix: define the hash as the canonical encoding of every input any rule reads: element ID, kind, parent, relationship ends, stored attributes, the derived interaction or the binding kinds, and the enabled rules. Add an ADR 0013-style fitness test that every mutation of a rule input changes the hash and that a layout or rename change does not.

### Should fix
- Self-relationships are treated inconsistently. In RUN-SYNC-CYCLE, a unit that calls itself synchronously is a High finding (RS6), so it is implicitly a remote call that holds a pool thread. In REL-NO-TIMEOUT, the same relationship has one runtime unit and is called in-process, so it gives nothing. Pick one meaning and apply it in both §3.3 'remote' and RS6/NT tests. Suggestion: a runtime unit's self-relationship is remote, because it goes over the network to its own endpoint.
- The §8 REL-SPOF judge table breaks the spec's own §2.2 rule ('Not checkable only if the unknown value could change the outcome'). (a) With zones = 1 and replicas unknown, a finding is certain: High if replicas = 1, Medium otherwise. AWS REL10-BP01's single-AZ anti-pattern also holds whatever the replica count. So report Medium 'one zone' and note that replicas are not stated. (b) With zones ≥ 2 and replicas unknown, the validate rule zones ≤ replicas implies replicas ≥ 2, so the result is nothing, not Not checkable.
- Interaction derived from port bindings (§2.4) mixes two different concepts. A sync binding is a rendezvous (a fused transition) and an async binding is a buffered place. Neither says whether the source waits for the answer. A request/reply modeled as two async relationships, as in E5's bag-based cases, comes out 'asynchronous' and locked. REL-NO-TIMEOUT and RUN-SYNC-CYCLE then say nothing, and the user cannot correct it. Proposal: the stored attribute is authoritative; bindings only suggest a value; validate reports a problem when a sync binding sits on a relationship stated as asynchronous. Also define what happens with a hand-edited file that has both a stored interaction and bindings, because FMT-1 forbids dropping unknown fields silently.
- The test tables in §4–§8 are not complete oracles. §9 says every model runs with all five rules and becomes an insta snapshot, yet the tables list other rules only 'where they interact'. Every model without a Person also gets the model-level REL-SPOF Not checkable entry, and most get REL-NO-TIMEOUT Not checkable entries (AC2 r3, RS1 r1–r3, SP1 r2, ...). Either enable only the rule under test, or list the full expected output. E8 hand-applies these tables, so they must be exact.
- The §9 notation is ambiguous: `{...}` after an ID means both children and attributes, and the spec does not say how an element with both is written. Use a distinct form for attributes, for example `container a [replicas=2] { component a1 }`. The golden-test parser depends on it.
- Finding keys are persisted in suppressions.toml, so they are format data under FMT-1. Define a canonical encoding: separator, escaping, and a namespace that keeps owner names apart from element IDs. Also fix the contradiction between §3.7 ('stable slug IDs only, never names') and the DATA-SHARED-DB key, which contains owner names.
- Rule isolation: §3.5 promises that one panicking rule gives 'internal error' for that rule only (ADR 0012). design.md §4 runs `scan::run(&model, &rules)` on a single `scan-*` thread. Say that each rule runs on its own supervised thread, for example `scan-<n>-<rule>`, or weaken the promise.
- `scan.disabled` is outside the brief, and v1-slices lists 'threshold tuning UI' as Out. It also lets a noisy rule leave the ≤ 20 % noise guardrail unseen. Either drop it from v1 (suppression with a reason is enough), or show disabled rules in the guardrail footer.
- The REL-SPOF remediation 'make the call ... degradable (a soft dependency)' cannot be recorded in the model, because there is no hard/soft attribute. The only way out is suppression. Say 'suppress as accepted, naming the fallback', or schedule a `hard` attribute later.
- LIM-2/LIM-4 bounds for the new inputs are missing: maximum length of owner and table names, maximum length of the tables list, the replicas and zones type and maximum (u32 newtype), and the maximum number of suppressions and file size of suppressions.toml. §3.4 also gives 2,000 elements as 'the LIM-2 limit', but LIM-2 requires headroom above that target.
- Cancellation: CODING_STANDARDS says scans run as engine jobs that can be cancelled. §3.9 says only 'needs no budget'. State that the scan polls the cancel flag, and what a cancelled scan shows. It must not be stale-looking-current.
- If relationship-level tables are kept: the DATA-SHARED-DB key does not change when the shared tables grow, for example from [orders] to [orders, payments]. An accepted suppression then silently covers new sharing. Add the shared table set to the key.
- §1 and §5 lean on E5 case 1 for timeouts and synchronous cycles. E5 actually shows that a timeout hid the starvation from deadlock and liveness properties, and only the share-of-pool predicate still found it. Reword so the citation does not imply that a timeout removes the risk; RUN-SYNC-CYCLE already says this correctly.
- P3 notes. The [V] claim that petgraph 0.8.3 tarjan_scc is recursive is confirmed: 'This implementation is recursive and does one pass over the nodes.' Before writing an own SCC, check whether petgraph's kosaraju_scc (built on its iterative DFS) is acceptable under LIM-3. The UX mockups use the rule IDs REL-SHARED-DB and REL-CALLBACK, which disagree with this spec's IDs; hand that to the UX designer. The claim that 'the kind field is part of the format from slice 0' is a format-spec decision; route it there.

## senior backend developer: approve-with-changes

### Must fix
- §4 step 3 (ARCH-CYCLE drops sets covered by a RUN-SYNC-CYCLE finding) leaves three things undefined. (a) `R` of a RUN-SYNC-CYCLE finding is never defined: §3.4 defines R(C) only on level graphs, not on G_run. If one implementation uses all carriers and another uses only synchronous carriers, they give different ARCH-CYCLE results when the same pair has both a sync and an async relationship (r1 a->b sync, r2 b->a sync, r3 a->b async). (b) If RUN-SYNC-CYCLE is disabled (§3.8 `scan.disabled`), or its thread panics (§3.5 'internal error' per rule), ARCH-CYCLE either cannot run step 3, or silently hides a real cycle that no rule now reports. (c) The witness of a RUN-SYNC-CYCLE finding picks 'the smallest ID carrier', which can be an asynchronous relationship, so the evidence for a synchronous cycle can show an async step. Fix: compute the G_sync strongly connected sets once as a shared fact, separate from rule enablement and suppression. Define R_sync(D) exactly. Drop ARCH-CYCLE sets only while RUN-SYNC-CYCLE is enabled and has succeeded. Pick witness steps only from synchronous carriers. Add tests for each case.
- §3.7/§3.8/§7: the finding key is saved to the project (`suppressions.toml`) but has no canonical encoding. Separator, level spelling, ordering and escaping are not defined. The DATA-SHARED-DB key mixes owner names (free user text) with element IDs. That contradicts §3.7 ('stable slug IDs only, never names'), and the two can collide: owner `billing` and container ID `billing` give the same key. Owner comparison is also undefined (case, whitespace). Fix: give an exact grammar with tagged identities (for example `DATA-SHARED-DB|db=orders-db|owner:orders|element:billing-worker`), state the normalization rule for owner (exact match after trimming, case-sensitive), and hand it to the format spec with an FMT-1 fixture. Two implementations, or two format versions, must produce identical bytes.
- §3.9: the scan's structural hash lists 'IDs, kinds, parents, relationships, attributes'. It does not list port-binding kinds, but §2.4 derives interaction from them. It also leaves out the `scan.disabled` set. Changing a binding from sync to async changes RUN-SYNC-CYCLE, REL-NO-TIMEOUT and REL-SPOF results without changing the hash, so stale findings show as Current (GLOSSARY Current/Stale). Fix: define the hash as the canonical encoding of exactly what `scan` reads, including binding kinds and the enabled rules. Add ADR 0013-style tests: every semantic mutation must change the hash, and changing insertion order or layout must not. Because display names are excluded from the hash, messages must also be rendered from current names when shown, as ADR 0013 does for replay.
- The spec does not say what the scan does on a model that has `validate` problems, and the loader deliberately admits such models (ADR 0001). Cases: a kind at the wrong level, a Container with no Software System parent, `zones > replicas`, relationship `tables` naming a table the Database does not list or set on a non-Database target, and an interaction attribute stored on a relationship that also binds ports (hand-edited file). In these cases `up`, `ru` and the REL-SPOF table, which relies on zones <= replicas, become partial functions. Two implementations will diverge or panic into 'internal error'. Fix: state the precondition. Either exclude elements and relationships with validate problems and report them like dangling ends (a count plus the problems panel), or refuse the scan with one model-level entry. Also state that a port binding wins over a stored interaction, and say what the loader does with the stored value.
- §6 judges REL-NO-TIMEOUT by the drawn source, and §2.4 defines interaction and `timeout` by the drawn source ('the source waits'). Every other rule uses the dependency direction from §3.1. Example: `d -> a sync timeout=no`, drawn as data flow ('returns rows to'), is really 'a waits on d with no timeout', yet the rule silently reports nothing. That is not a Not checkable entry, so a known missing timeout passes as clean. It is also unclear which side `timeout` describes on a reversed relationship. Fix: define interaction and `timeout` in dependency direction (the dependent side waits and gives up), judge each relationship on dep(r), and add a test where a Database is the drawn source.
- §7 contradicts §2.2. §2.2 says nothing is assumed and that an unknown value that could change the outcome gives Not checkable. DATA-SHARED-DB instead reads an unknown `owner` as 'each container is its own service', which is an assumed value. The spec's own cited C4 Microservices page says one service is 'one or more containers', so `owner` can change the outcome. This is the most common real design (an API container and a worker sharing their own database) and the first threat to the ≤ 20 % 'not real' guardrail. Fix: choose one. Either (a) report Not checkable 'owner' when there are two or more identities only because owners are unknown (still a finding when known owners differ or when an outside system accesses the database), or (b) keep the finding but add an explicit exception to §2.2 and list it in §10 as a deviation, with E8 measuring the noise.
- Test AC3 contradicts itself: it says 'Two findings', then '(2) None other'. Test models are the implementation contract. Fix the text to one Container-level finding with the Component set folded into it, and add the missing opposite case: an extra one-way relationship between other children, so R(C') ⊄ R(C) and two findings remain.
- Glossary compliance (brief: 'use its terms exactly'). (a) The front matter promises that new terms are listed in §10, but §10 lists none. The spec uses many new terms: runtime unit, level graph, lifted relationship, finding key, interaction, remote, accessor, identity, entry point, disposition, Not checkable entry, required/refinement attribute. (b) 'Witness cycle' uses a GLOSSARY _Avoid_ word (Evidence: avoid 'witness'), which TXT-1 forbids in the UI; rename it, for example to 'example cycle'. (c) GLOSSARY defines Not checkable for an element, but the spec applies it to relationships, cycles and the whole model. (d) GLOSSARY defines Suppression as 'the decision to accept a finding', but the spec adds a 'not real' disposition. Fix: add the term list with proposed glossary text, and propose the amendments for Not checkable and Suppression explicitly.

### Should fix
- §3.4: petgraph's `kosaraju_scc` is documented as 'iterative and does two passes over the nodes' (docs.rs, petgraph 0.8.3, checked 2026-11-02). LIM-3 is therefore no reason to write our own SCC algorithm. Either use `kosaraju_scc` or give a different reason, and correct the §10 deviation entry.
- §4 step 2: the fold condition R(C') ⊆ R(C) does not match its own definition ('the higher cycle exists only because of the lower one'). One unrelated one-way relationship between other children of the same parents blocks folding and produces a duplicate finding. Suggested condition: C' is no longer strongly connected in G_{L+1} once the carriers in R(C) are removed. Folding can also hide a real cycle inside one parent that survives the fix (AC3's a1 <-> a2). List those sub-cycles in the evidence.
- §5 step 3: the missing data includes unknown carriers on lifted relationships that already have a synchronous carrier. Stating those cannot change the outcome, which contradicts §2.2. Only list unknown carriers of lifted relationships that have no synchronous carrier.
- §8 judge table: the 'replicas unknown | any' row gives Not checkable where `validate` (zones <= replicas) already decides the outcome. zones >= 2 means nothing to report. zones = 1 means a finding in either case (Medium 'one zone', or High if replicas = 1). Split the row. Also define 'the shortest path' used for the interaction Not checkable entry as the BFS predecessor path of step 3, with ties broken by ID order.
- §3.7 says every finding has a level, but the level is only defined for the cycle rules. Define it for REL-NO-TIMEOUT (for example the level of the lower end), DATA-SHARED-DB (Container) and REL-SPOF (the judged element's level), so the panel can navigate.

## Decisions

- Interaction is always a stated relationship attribute; port bindings never set or override it. The convention is that one relationship carries a call and its reply binding. A sync binding against a stated 'asynchronous' gives a validate warning, the inspector offers a one-click suggestion, and nothing is dropped. — A sync binding is a rendezvous and an async binding is a place. Neither says whether the caller waits. E5 case 1 replies are reverse sync bindings, and E5 case 3 waits over async bindings. Deriving interaction would create false High cycles or lock waiting callers to 'asynchronous'. This resolves PM M1 (a)-(d) and the architect's interaction item with one mechanism.
- Drop relationship-level and database tables from v1. Schema-per-service is drawn as separate Database elements, and private tables in one schema are suppressed as accepted. — north-star.md decided non-goal: tables appear at most as an attribute of Database elements. Cutting them is the thinnest path that respects a decided item.
- DATA-SHARED-DB: different Software Systems, or stated services that differ, give a finding. Within one system, a service that is not stated gives Not checkable. The attribute is renamed owner -> service. — This makes §7 obey §2.2 ('nothing is assumed'). C4 models a service as one or more containers and promotes a separate team's service to a Software System (re-verified). It protects the 20% 'not real' guardrail.
- ARCH-CYCLE fold condition changed to necessity: C folds into C' when C' stops being strongly connected after removing the lifted relationships carried only by R(C). In-parent cycles of a folded set are reported as their own findings. — Fixes the contradictory AC3, keeps one cause one finding, and stops one suppression from hiding an independent cycle (architect, backend).
- Coverage of ARCH-CYCLE by RUN-SYNC-CYCLE is computed from a shared G_sync fact inside ARCH-CYCLE. Sets are compared by runtime-unit member sets. A covered finding is hidden at display time only while RUN-SYNC-CYCLE ran successfully and its finding is not suppressed as not real. — A real cycle can no longer vanish when the other rule is absent, panics or is marked not real. Suppression stays a display-time join with no rescan (PM M6, architect, backend).
- No per-project rule disabling (scan.disabled) in v1. scan::run keeps a rule list for tests. — Not in the brief. v1-slices puts threshold tuning out of scope. Disabling hides noise from the guardrail and creates cross-rule dependency problems.
- Use petgraph kosaraju_scc instead of writing an own SCC. — Verified on docs.rs (petgraph 0.8.3): 'iterative and does two passes over the nodes', so it meets LIM-3.
- One supervised thread per rule (scan-<n>-<rule-id>). The scan is a cancellable job, and a cancelled scan shows no partial results. — ADR 0006 bans catch_unwind, so per-rule isolation needs a thread per rule. The scan-* prefix keeps ADR 0012 unchanged. CODING_STANDARDS requires cancellable jobs.
- The staleness hash is the scan input hash: exactly the attributes and structure the rules read, plus the rule list. Bindings, names, layout and suppressions are excluded. Messages are rendered from current names. — Architect and backend: findings must never look current after an input change, and must not go stale on rename or layout. Bindings are no longer inputs.
- REL-NO-TIMEOUT judges each relationship in dependency direction. A runtime unit's self-relationship is remote in both RUN-SYNC-CYCLE and REL-NO-TIMEOUT. — A drawn data flow from a Database would otherwise hide a known missing timeout. It also gives one consistent meaning of 'remote'.
- The REL-SPOF judge table follows §2.2: zones=1 is a Medium finding whatever replicas are, and zones>=2 gives nothing because validate implies replicas>=2. The path is the BFS predecessor path. — Not checkable only when stating the value could change the outcome. AWS REL10-BP01's single-AZ anti-pattern holds whatever the replica count (re-verified).
- Canonical finding-key grammar with IDs only, sorted byte-wise. The format spec must keep '|', '=' and ',' out of slugs. — Keys are persisted (FMT-1). Owner names in keys collided with IDs and contradicted 'never names'.
- Tests list their enabled rules and complete expected output. Attributes use [ ] notation. Added tests: E5 case 1, disabled, suppressed and panicking sync rule, sync+async pair, G_su containing a G_sync finding, Code-level fold, dangling end, Database as drawn source, key stability. — The tests are the golden oracle and the E8 dry-run input, so they must be exact (all three reviewers).

## Proposed glossary changes

- **Not checkable**: Said of a rule that could not be applied to a subject (an element, a relationship, a set of elements or the whole model) because the model lacks the data it needs, for example a timeout that is not stated. Each case is a Not checkable entry that names the missing data. _Avoid_: Unknown (reserved for verdicts), n/a, skipped, open
- **Suppression**: The user's decision about a finding, with a written reason and a disposition: accepted (the finding is real and the user accepts it) or not real (the rule is wrong here). A suppressed finding stays visible as suppressed. _Avoid_: Ignore, waiver, exception, baseline
- **Not stated**: The value of an attribute that the model does not give. A rule never treats it as yes, no or a number; it leads to Not checkable when stating it could change the outcome. _Avoid_: Unknown, null, default, n/a
- **Interaction**: Whether the dependent end of a relationship waits for the other end's answer before it goes on: synchronous or asynchronous. Stated by the user; port bindings never set it. _Avoid_: Sync flag, call type, mode
- **Timeout**: A relationship attribute: the dependent end gives up waiting after a set time, on both connection and request. It is not the Budget of a check. _Avoid_: Deadline, Budget
- **Runtime unit**: An element that runs or stores data on its own: a Container, Database, Queue, or a Software System without children. Components and code elements run inside their container. _Avoid_: Process, deployable, node, service
- **Example cycle**: The one shortest cycle that a cycle finding shows, step by step, with the relationship behind each step. _Avoid_: Witness, trace, path
- **Severity**: How serious a finding is: High or Medium. _Avoid_: Level (a C4 level), priority, error/warning
- **Service (attribute)**: The name of the service a Container belongs to; containers of one Software System with the same service count as one service. _Avoid_: Owner, team
