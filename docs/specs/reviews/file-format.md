# Reviews and disposition: File format spec v1

Author: senior backend developer. Final document: `docs/specs/file-format.md`.

## software architect: approve-with-changes

### Must fix
- Overall: the storage machinery (§2 layout, §3 strictness, §9 entities, §11 writer, §12 versioning, §13 journal, §15 merge analysis) is sound and well verified. The schema sections (§4, §6, §8, §14) were not rebased on the final upstream specs, though the brief says to adopt their shapes. Each item below is a direct contradiction. The draft's §17 line "No other ADR is contradicted" is therefore wrong, and the open questions §18 Q1, Q2 and Q4 are already answered upstream (PL §9.2 and OQ12, NS §6.2 and §16.1, NS §2.2) and must be closed.
- §4.1 and §4.3, the ID alphabet and collision suffix, contradict CODING_STANDARDS FMT-3 (`order-api`, `order-api-2`) and every upstream spec. Upstream examples use hyphens: SM `cool-down`, `closed-failure-2`; PL `api-jobs`, `worker-replies`, `az-a-pool-share`, built-in id `deadlock-free`, and E-32 `waiting-2`; scan `order-api-10`. The reason given for banning hyphens ("`-` is the minus sign") is already settled by NS §5.3 maximal munch. Fix: allow `-`, use the `-2` suffix, and reserve `and`, `or` and `not` (NS §2.2 and §16 item 12, which the draft does not do). Forbid `__` in behavior-model names (SM §1.3, F1). Keep `|`, `=` and `,` excluded (scan §2.7). Lowercase-only for element and relationship IDs, because they are file stems on case-insensitive file systems, is a legitimate narrowing. If kept, state it as a narrowing of NS §2.2 and flag that the slice 4 acceptance text `Billing/inflight` and PL P-09 need lowercase IDs.
- §4.4 re-derives the ID from the name until the first Save. This contradicts FMT-3 ("created once … never change on rename") and is not flagged as a deviation. Either drop it, or list it in §17 as a proposed FMT-3 change, with its effect on journal images, undo snapshots and CheckKeys stated.
- §4.3 "Taken" omits PL §4.5 and A10. The generator must never issue an ID that any property, final predicate, template parameter or suppression key still references, whether that reference resolves or dangles. Without this rule, an old property silently retargets to a new place (E-32), which is a wrong-verdict path.
- §6.6 and §10.3 say that in a combined scope a place port is `unbound` and that binding a place port is `incompatiblePorts`. This contradicts NS §6.2, §16 item 1 and L4: only transition ports must be bound, and place ports are never bound but are what a combined-scope property may name. As written, every place port blocks lowering. Fix: L4 applies to transition ports only. A binding that names a place port is an L5-style error. Remove the line saying place ports are unbound.
- §6.8 lets predicates name any place, and §17 proposes an ADR 0003 clarification in that direction. Both contradict NS L9, which is in force pending NS OQ1 and PL OQ1, and the recommendation in NS and PL. The format must store and validate against L9 (PL §4.3 rule 5, E208) and must not propose a contrary ADR change on its own. Drop the §17 ADR 0003 item, or recast it as "pending OQ1".
- §6.8 properties do not use the PL §9 shape the format spec is told to adopt. Required changes: (a) `behavior = "own" | "combined"`, not `about = own | children` (the glossary scope wording and PL forbid `scope`/`children`); (b) the `kind` set adds `deadlock_free`, `no_capacity_exceeded` and `no_dead_transitions`, and built-ins are explicit stored entries seeded by New project (PL §9.2, J6, OQ12), not implicit with reserved names (§18 Q1 is answered); (c) `id` is unique per project, not `element/about/name`; (d) add `label` and the template keys `template`, `template_version` and the parameters, with the PL writer key order; (e) the limits of 256 properties per element and 4,096 per project (E409); (f) `[final]` with `own` and `combined`, not `[final_markings]` with `children` (the glossary/NS term is final predicate). If the format prefers keyed tables over `[[property]]` arrays for entity paths (§9.1), propose that as a PL amendment and do not diverge silently.
- §6.9 defines a second predicate grammar. It lacks `==`, `not not`, the ID lexer with `/` and `-`, and i32 limits, so it would accept or reject different texts from NS §5.3. Delete it and cite NS §5.3 / PL §3.2 as normative. The loader runs the same `model::property` parser.
- §6.7 relationships and bindings. (1) There is one `binding` sub-table with one `from_port`/`to_port` pair, but upstream needs several pairs per relationship. NS C3 has two fusions on one relationship. SM §2.2 says a relationship binds one or more (port, port) pairs. Scan §2.5 makes "one relationship carries a call and its reply" the convention (RS9). L8 allows at most one async pair, and L12 forbids duplicate pairs. (2) `sync` is used both as the scan attribute and as the binding mode, and it is required once a binding exists. Scan §2.5 rules that interaction is stated by the user and never derived from bindings: a request/reply over two async bindings is still synchronous interaction (E5 case 3). Fix: give each binding pair its own `mode = sync|async` (async pairs carry `capacity` and `when_full`). Store the scan's `interaction` separately, with the values synchronous or asynchronous or absent. (3) A binding between non-siblings is `badBinding`, which blocks scopes. NS §6.6 treats a non-contributing relationship as an assumption, and L4 handles ports bound only from outside. Align with NS rather than adding a blocking error.
- §6.3 attributes contradict the scan spec. Scan §2.3/§2.4 define `replicas` and `zones` (count 1..1000, `Count(u16)`), `service` (name 1..64 characters), relationship `interaction` (synchronous/asynchronous) and `timeout` (yes/no). It explicitly removes `owner` (renamed because a team name merges services), `logical_db` and `tables`, and has no `entry_point` (entry points are relationships from a Person). The format may choose its own encoding (bool versus "yes"/"no"), but names, value sets and ranges must match, and the draft's wording "not set (unknown)" must become "not stated" (scan §2.2, GLOSSARY Not checkable: Unknown is reserved for verdicts).
- §5 `[scan] disabled_rules` contradicts scan §2.7 and §11: v1 has no per-project rule disabling, because it would hide noise from the guardrail. Remove it.
- §8 suppressions contradict scan §2.7 and §3.7–3.8. The required shape is a `[[suppression]]` array sorted by key with `key`, `disposition` (`accepted` | `not-real`), `reason` (1..500 characters after trimming) and `date`. The key encoding is `RULE|field=v,…` (for example `REL-SPOF|element=d|defect=one-replica`), not `RULE(id,…)`. The draft's keys cannot represent `level=`, `database=` or `defect=`, so suppressions would not survive or would match the wrong finding. Add the LIM-2 limits of 10,000 entries and 4 MiB, checked before parsing.
- §6.5 state machine schema contradicts SM §1.1–1.5 and §8.3. Missing: an explicit events table with `direction = input|output|internal` (three-valued, F7); state, event and transition display `name`; the `final` list of states (SM-E09); and one namespace across states, events and transitions (SM-E04; the draft keeps events separate). The draft rule "every event is a port" contradicts SM A2: internal events are not ports and fire alone, which is how E5 models timeouts. Inferring events from transition values makes SM-E07 (undeclared event) and SM-E11 (unused port event) impossible to report. The final TOML syntax is the format's to choose (`[state_machine]` versus SM §1.5's `[behavior] kind`), but the content must match, and the SM limits (1,024 states, 1,024 events, 4,096 transitions) must be checked before the tables are parsed (SM §12).
- §3.3 and §10.5 strictness granularity contradict SM-E10 and PL E407. An unsupported key in a behavior model must load the element with `BehaviorModel::Unloaded` (it stays in the Model, and its scopes fail L1). An unknown key in a property entry is kept verbatim, reported as E407, and only that property is not checked. The draft instead drops the whole element file, which removes the element and forces broader blocking. Specify strictness per section: file/element top level → file not loaded (current rule); behavior section → Unloaded; property entry → E407. FMT-1 ("never dropped silently") is met in every case.
- Load-time limits are missing (LIM-2 "must"; scan §3.4 explicitly relies on "the format spec's LIM-2 limits on load"). Specify the maximum file size checked before parsing, and the maximum elements, relationships, places, transitions and arcs per net, string lengths, property counts and suppression counts. State which problem each limit produces and that it is checked before allocation.
- §14 example project, as a literal artifact, would not produce the stated "no problems" or the stated verdicts under the upstream rules. (a) `users` is a `person` with `parent = "cognito"`, but scan §2.1 and §3.10 say a Person has no parent, so this is a validate problem and the element is excluded. Use a Container stand-in, as was done for `kinesis_api`. (b) `fe1/map_entries` (property) and `users/signed_in` (final predicate) are not place ports, so under L9 both are E208 / ModelIncomplete, not the listed verdicts. Mark them `port = true`. (c) The suppression `REL-SPOF(kinesis_api)` has the wrong key format and matches no finding: `kinesis_api` has `zones = 3` and no Person flow, so it would be `orphanSuppression`. (d) Built-ins must appear as explicit `[[property]]` entries, with IDs per PL. (e) Re-express all files in the corrected shapes, with hyphenated IDs where natural, re-run the throwaway loader and `e5/explore.py`, and state which values are oracle facts (for example 330 markings on a Disproved) rather than evidence (NS §14 convention).

### Should fix
- §3.4 ranges: `capacity` ≤ 2^31−1 is narrower than NS u32 (cap + max post weight ≤ u32::MAX, rule 7). Say why it is narrower: predicate constants and template expansions are i32 (PL E308). Also say that NS vectors V51–V54 are net-level only and cannot be written as files.
- §13.5 step 5: when a relationship's source is reconnected, its entity moves between files, so the last image has a different `file`. State that applying an image also removes that entity key from any other file. Otherwise restore can duplicate a relationship and produce `duplicateId`.
- §12.2 and §12.3: lazy per-file upgrade plus a project step that runs "only after every file reached n" is ill-defined after a partial Save (conflict-skipped files), because some files are then at n+1 and some at n. Either require every file touched by a project step to be written eagerly in one Save, or require project steps to be idempotent per file and keyed by each file's own `format`.
- §9.1 entity paths assume keyed tables. If PL's `[[property]]` and scan's `[[suppression]]` arrays are adopted, define entity identity by the `id`/`key` field and not by array position, both for journal after-images and for per-entity reload. Alternatively propose keyed tables to the PL and scan owners. Pick one before journal goldens exist.
- §4.4 renaming a place, transition or state rewrites its ID. SM states, events and transitions have a separate display `name` (SM §1.1). Give Petri net places and transitions an optional `name` too, so that a display rename never changes a qualified ID or a CheckKey (FMT-3, ADR 0013).
- §17 records `suppressions.toml` and `arch.toml` as "ADR 0001 made concrete (no change)". Scan §2.7 asks for an explicit amendment to ADR 0001's file list. List it as a proposed amendment with its replacement sentence.
- §2.4 New project: once PL OQ12 is decided, seed the explicit built-in property entries (`deadlock_free` and `no_capacity_exceeded`, behavior combined) on the system element.
- §14: tag the example's slice. Two parent systems means drill-down (slice 3), and properties and finals are S4. In slice 0 the six elements form one scope (NS §13.2). Consider adding the ADR 0014 variant (`cognito_web/buf(2, block)`) as a second fixture, so that `block` round-trips in a golden.
- §10.3: map each problem kind to the NS L-rule or SM/PL code it feeds (for example noWhenFull → L2, badInitial → L10, a missing capacity on an async pair → L13), so that ModelIncomplete detail lines and Problems entries stay one cause with two renderings (SM §8.1).
- §6.2 says format 1 does not restrict kind against level. Point to scan §3.10 (kind/level/parent mismatch is a validate problem that excludes the element from scan rules), so the two specs do not appear to disagree.

### Questions for the user
- The upstream specs conflict on reply bindings. Scan §2.5 and its test RS9 put a reply binding on the call's relationship as a pair from a target port to a source port (`control_plane.ret_a -> api_a.reply` on `r1: api_a -> control_plane`). NS L11 requires every fusion caller to belong to the relationship's source element, and SM-B01 allows an output event only at the source end. The format spec cannot store RS9 legally until this is settled. Which do you want: (a) relax NS L11 and SM-B01 so that each pair names its caller element explicitly, and the fused ID stays `relationship/caller+callee` with bare names (unique because L12 applies per pair), or (b) change the scan convention so that replies are separate relationships, which RUN-SYNC-CYCLE then reports as call cycles (RS9b)? Recommendation: (a). The format stores each pair with qualified ports (`from = "control_plane/ret_a"`), and L11 becomes "each pair binds one port of each end".
- Do you accept the draft's lowercase-only rule for element and relationship IDs? Element IDs are file stems, so `Billing` and `billing` would collide on Windows and macOS. If yes, the slice 4 acceptance text "never Billing/inflight + Shipping/inflight > 2" and PL P-09 need lowercase IDs (the UI still shows display names). Recommendation: yes. Hyphens stay allowed per FMT-3.

## researcher: reject

### Must fix
- Properties do not follow the shape the property-language spec fixes in §9 for this spec (its A10). Draft §6.8 and §4.2 use `[properties.<name>]`, `about = "children"|"own"`, `kind` limited to never/always_reachable, built-ins implicit with reserved names, property names unique per element, and IDs of the form `element/about/name`. The property spec requires `[[property]]` entries with these keys: `id` (a slug unique in the project), `label`, `behavior = "own"|"combined"` with no default, `kind` covering all five kinds (deadlock_free, no_capacity_exceeded, no_dead_transitions, never, always_reachable), `predicate`, `template`/`template_version` plus template parameters (OQ4), the writer order of §9.2, and limits of 256 per element and 4,096 per project. Built-ins are explicit entries, and New project seeds deadlock_free and no_capacity_exceeded with behavior = "combined" (§9.2; draft §2.4 seeds nothing). Rewrite §4.2, §6.8, §9.1 (entity keys for an array of tables), §11.1 (key order) and the §14 example to match.
- Final predicates: the draft's `[final_markings]` with keys `children`/`own` contradicts property-language §7/§9.1, which uses `[final]` with keys `own`/`combined`. The draft also uses the term "final markings" where NS §17 uses "final predicate". Adopt `[final]` and the glossary term.
- Draft §6.8 says "predicates may name any place, not only port places" and proposes amending ADR 0003 that way (§17, Q3). This contradicts NS §6.6 L9, which is in force, and NS §16 item 3. Under L9 a combined-scope predicate may name only place ports and generated places; the user decides once, as NS OQ1 / property OQ1. The format spec must not pre-empt that decision. Drop §17's first bullet and refer to OQ1. As a consequence, the §14 example is wrong under the current rules: `fe1/map_entries` (P2) and `users/signed_in` (the final predicate) are not ports, so both scopes' properties end Unknown ModelIncomplete (`... is not a port`). NS §13.2 declares them as place ports, and the example must do the same.
- Place ports: draft §6.6 and the `unbound` row of §10.3 make an unbound place port an error in a combined scope, and a binding that names one `incompatiblePorts`. Q2 recommends dropping `port` on places altogether. This contradicts NS §6.2 and §16.1: place ports are never bound, exist so that parent-scope properties can name them, and L4 applies to transition ports only. As written, any model that uses a place port (needed for L9) can never be checked in a combined scope. Limit `unbound` to transition ports and to state machine input/output events. Close Q2 as answered by NS §6.2.
- A relationship can hold only one binding (draft §6.7: a single `[relationships.<id>.binding]` sub-table). NS L8 allows any number of fusions per relationship and at most one AsyncLink. NS C3 has two fusions on one relationship (`ra/take+acq`, `ra/give+rel`). State machines §2.2 says "a relationship binds one or more (port, port) pairs". The scan spec §2.5 convention puts a call and its reply on one relationship. Bindings must be a list, for example `[[relationships.<id>.binding]]` or a keyed table, and each entry needs its own mode (sync or async). Also specify the per-relationship rule that at most one entry is async (L8), and that duplicate (from_port, to_port) sync pairs are rejected (L12).
- Draft §6.3 and §6.7 merge the scan's interaction attribute with the binding mode into one `sync` bool ("A binding needs `sync` to be set"; `sync = true` with `capacity` is `badBinding`). Scan spec §2.5 says explicitly that interaction is stated by the user and that bindings never set or override it. E5 case 3 is a request and reply over two async bindings by a caller that waits, so it needs interaction = synchronous on async bindings, and the draft cannot express that. Store interaction separately (scan §2.6 proposes `interaction = "synchronous"|"asynchronous"`) and the mode per binding. Add the §2.5 `validate` warning for interaction stated asynchronous while a sync binding has its `from` port in the source.
- The scan attributes in draft §6.3 do not match scan spec §2.3/§2.4/§2.6. The draft has `owner`, `entry_point` and `logical_db`, and allows `replicas`/`zones` on software_system and component with a range up to 2^31−1. The scan spec has `service` (Container and Database; 1–64 characters; renamed from owner on purpose, because a team name silently clears DATA-SHARED-DB findings), `replicas`/`zones` only on Container, Database and Queue with range 1..1000, a `zones <= replicas` validate rule, and no logical_db or tables. Entry points are Person relationships, not an attribute. `timeout` is yes/no/not stated. The draft's tri-state bool is an acceptable encoding of timeout, but use "not stated", not "not set (unknown)": the glossary reserves Unknown for verdicts, and scan §2.2 says the files say "not stated". The draft also ignores the out-of-range handling of scan §3.10 (a failing value is treated as not stated).
- Suppressions in draft §8 do not match scan spec §2.7/§3.7/§3.8. The draft uses `[suppressions."RULE(id,…)"]` with `reason` up to 10,000 characters, `created`, and no disposition, and says dispositions are not in format 1. The scan spec requires a `[[suppression]]` array sorted by key with `key`, `disposition` ("accepted"|"not-real", which the noise guardrail needs), `reason` (1–500 characters after trimming), `date`, the key grammar `RULE|field=a,b|…` (for example `REL-SPOF|element=d|defect=one-replica`), and LIM-2 limits (at most 10,000 entries and 4 MiB, checked before parsing). The suppression in the §14 example has to be redone too.
- `[scan] disabled_rules` in `arch.toml` (draft §5) contradicts scan spec §2.7/§11: "There is no per-project rule disabling in v1", because disabling would hide noise from the ≤20 % guardrail. Remove it, or raise it with the product owner as an explicit deviation.
- State machine storage (draft §6.5) lacks data that state-machines spec §1.1/§1.5/§2 requires. States have no display `name` (the draft says "a state table accepts no keys"). There is no events table with `direction` = input|output|internal; the draft instead says "every event is a port", which contradicts amendment A2 (internal events are not ports and fire on their own). There is no `final` list. As written, every timeout/internal event would be `unbound` in a combined scope, and E5-style timeouts could not be modeled. The format spec owns the syntax, but it must carry: states with names, events with direction and name, transitions with explicit IDs and from/event/to, initial, final, and SM-E10 (unknown key or direction is a load error).
- Section 6.9 is a second predicate grammar that differs from NS §5.3. It lacks `==`, allows only one `not` (`conjunct = ["not"] atom`), and uses a different ID lexer. The property spec withdrew its own second grammar for exactly this reason (§1, rev. 2). Replace §6.9 with a reference to NS §5.3 and property-language §3.2, and keep only the storage rules (stored verbatim; length ≤ 4,096 bytes per property §3.2).
- Slug and ID rules conflict with every upstream spec and with CODING_STANDARDS FMT-3. Draft §4.1 uses `[a-z][a-z0-9_]{0,47}` with suffix `_2`. NS §2.2 allows `[A-Za-z_][A-Za-z0-9_-]*` and reserves `and`, `or`, `not` (missing from the draft). The state machine spec reserves `__` (missing). FMT-3, property §4.5 (`waiting-2`, vector E-32) and state machines §1.3 (`closed-failure-2`, `trip-2`) use a `-N` suffix. The vectors use `api-jobs`, `worker-replies`, `rel-7`, `cool-down` and `a-get-l1`, and the slice 4 acceptance example uses `Billing/inflight`. NS says the format spec may narrow slugs further (length, reserved words), and lowercase-only is well motivated by case-insensitive file systems. But excluding `-`, changing the suffix and forbidding upper case are changes to FMT-3 and to upstream fixtures. List them as proposed amendments with the vectors affected, or adopt NS's alphabet. In either case, add the `and`/`or`/`not` and `__` reservations.
- Silent retargeting is a path to a wrong verdict. The draft's "taken" set (§4.3) covers the current model, the saved snapshot, files on disk and, for behavior names, only the names already in that element. It does not include IDs that properties, final predicates or template parameters still reference. Property-language §4.5 (A10) requires that the slug generator never issues an ID that is still referenced, dangling or not. Example: place `api/waiting` is deleted and saved, while a `never api/waiting >= 3` property stays dangling. Under the draft, a new place named "waiting" gets `waiting`, and the old property silently checks the new place (vector E-32 expects `waiting-2`). The same applies to element and relationship IDs. Also, draft §4.4 re-derives IDs before the first Save, which contradicts FMT-3 ("created once … never change on rename"). Either drop that rule or record it as a proposed FMT-3 amendment, and in either case keep re-derivation away from referenced IDs.
- Renaming a place, transition or state (draft §4.4, [S1]) changes its ID, because places, transitions and states have no display names. This contradicts FMT-3 (IDs never change on rename) and state machines §1.3/§9: a display-name change of a state, event or transition must not change the key, which vector K-04 asserts. Give states, events and state machine transitions a `name` key as the state machine spec requires, and decide whether Petri net places and transitions get one too. A rename must then be a display-name change.
- The strictness granularity in draft §3.3/§10.5 (any unknown key → the whole file does not load) conflicts with two upstream rules. Property-language §9.2 (E407, vector E-31): unknown keys in a `[[property]]` entry are kept verbatim on save, and only that property is not checked; the reserved `final` key must not block the whole element. State machines §1.4/§8.1: an SM-E10/E12 load error keeps the element in the Model as `BehaviorModel::Unloaded`, so L1 fails for exactly the scopes that contain it. Specify per-section failure (behavior → Unloaded, property → E407, other keys → file problem) and keep §10.5's blocking rule for files that are not valid TOML.
- LIM-2 limits are missing. CODING_STANDARDS LIM-2 requires input to be checked against limits before allocation, and upstream specs defer those limits to this spec. Needed: element and relationship counts per project (the scan spec says its loops are bounded by the format spec's LIM-2 limits on load), a maximum bytes per file checked before parsing, places, transitions and arcs per net, SM_STATES_MAX/EVENTS/TRANSITIONS (state machines §1.4, "checked before tables are parsed", §12), the property limits (256 per element and 4,096 per project; predicate ≤ 4,096 bytes), the suppression limits (10,000 entries, 4 MiB) and layout entries per view.
- The complete example (§14) cannot be the golden v1 fixture as written. It uses the wrong shapes for properties, finals, attributes (`entry_point`, `owner`), the `sync` bool, bindings and the suppression. It has no place ports for L9. It omits the explicit built-in property entries. And it places a `person` (`users`) at Container depth inside `cognito`, which scan spec §2.1/§3.10 treats as a kind/level validate problem that excludes the element from every rule. Regenerate it from the adopted shapes and re-run the E5 reproduction. Also state whether `users` should be a container stand-in (NS OQ4).

### Should fix
- Add a kind/level/parent validate problem. Scan spec §2.1/§3.10 needs every kind to belong to one level with a parent of the right kind (Database and Queue under a Software System; Person and Software System top-level). Without it, the scan's exclusion rule has nothing to read. Draft §6.2 says "format 1 does not restrict which kind sits at which level".
- Draft §6.7 says "A relationship from an element to itself is badBinding". Clarify that this applies only to bindings (NS L6). Scan spec RS6 and NT8 depend on self-relationships of a runtime unit being legal model data.
- Initial above capacity is ambiguous. §3.4 lists `initial` with range 0..=capacity (§3.3 makes out-of-range a schema error, so the file does not load), but also names the problem `badInitial` (the file loads). NS V29 expects the file to load and the scope to end Unknown ModelIncomplete with `x/p: initial 5 exceeds capacity 3`. Remove capacity from the schema range and keep `badInitial`.
- Capacity and weights are capped at 2^31−1 (§3.4), which narrows NS §2.3 rule 6 (u32). This is reasonable: it matches property E308 and makes NS rule 7 unreachable from files. State it as a deliberate narrowing, and note that NS V51–V54 are then net-level vectors only.
- Windows MAX_PATH arithmetic in §2.1 leaves out the temp file. A 180-character project path plus `\elements\` plus a 48-character ID plus `.toml` is 243 characters. The §11.4 temp name `.<id>.toml.<pid>-<n>.tmp` adds about 20 characters, about 263 in total, which is over MAX_PATH (260, terminating null included; Microsoft Learn, Naming Files: https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file). Either budget the temp name or use a short temp name such as `.<n>.tmp`. The reserved device-name list in §4.3 matches that page; the superscript COM/LPT variants are excluded by the ASCII alphabet. Microsoft also says `NUL.txt` is equivalent to `NUL`, which confirms that `con.toml` is unusable.
- Section 11.4: on Windows, rename-over can fail with a sharing violation while an editor, an indexer or antivirus holds the target. Specify a bounded retry, and report a failed write (not a conflict) after the retries.
- Journal lock (§13.1): `File::try_lock` is stable since Rust 1.89 and returns `Result<(), TryLockError>`. Only `TryLockError::WouldBlock` means another holder; `TryLockError::Error` (for example an unsupported or network file system) must be handled separately and not reported as "open in another window". The lock may be advisory or mandatory depending on the platform (flock with LOCK_EX|LOCK_NB / LockFileEx; https://doc.rust-lang.org/std/fs/struct.File.html).
- Journal directory key (§13.1): hashing the canonical absolute path on Windows depends on case and on the `\\?\` prefix from `canonicalize`. One project opened under two spellings would get two journals, and a restore could be missed. Normalize the path (strip the verbatim prefix and case-fold on Windows and macOS) before hashing. Tauri's `app_local_data_dir` is `local_data_dir/<bundle identifier>` unless `appDirectoriesOverride` is set (https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html). A CLI must therefore also honor that override to compute the same path.
- Journal example §13.7: the `Delete Users` change images `element:users`, `relationship:sign_in` and the layout entry, but not `behavior:users`, which lives in the same deleted file. Specify cascade semantics: either an element-deleted image implies deleting every entity of that file, or every contained entity is imaged. Otherwise a replay can leave a behavior entity with no file. The base record lists only 3 of the 13 files; under step 3 of §13.5 (E ∪ D ∪ P) such a journal would always mismatch. Mark the listing as elided, or list all files.

### Questions for the user
- Slug alphabet: keep NS §2.2 and FMT-3 (hyphens allowed, `-2` collision suffix, upper case allowed), or adopt the draft's lowercase, underscore-only `[a-z][a-z0-9_]{0,47}` with a `_2` suffix? ## Decisions

- IDs use FMT-3 slugs: hyphens are allowed and the collision suffix is -2. Element, relationship, view and property IDs are lowercase only, start with a letter, do not end in '-' and have at most 48 characters. Behavior-model names use the NS 2.2 alphabet with no '__' and no trailing '-'. and/or/not and the Windows device names are reserved. — This matches FMT-3 and every upstream vector. Element IDs are file stems, and a stem that differs only in case is the same file on Windows and macOS. The narrowing is stated as amendment A2, pending Q2.
- IDs never change on rename. Every part has a display name: places and transitions now have one too. The rule that an ID follows the name until the first Save is withdrawn. — FMT-3 and ADR 0013 (display renames never change the CheckKey; SM K-04). This also keeps journal images and undo simple.
- The slug generator's taken set includes every referenced ID, resolved or dangling. That covers predicates, final predicates, template parameters, binding ports, layout entries and suppression keys. — Otherwise a new place could silently become the subject of an old property, which is a wrong-verdict path (PL 4.5, E-32).
- Strictness is per section. At the element level, including relationships and [final], a failure means the file does not load. In a behavior section, the behavior becomes Unloaded (L1). In a property entry the property gets E407 and is kept, but not checked. — This follows SM-E10 and PL E407. A dropped relationship could remove a fused alternative and shrink a net, so relationship-level errors stay file-level.
- Binding pairs are stored as a [[relationships.<id>.binding]] array. Each pair has mode = sync|async and qualified from/to ports, and an async pair also has capacity and when_full. The scan attributes interaction and timeout are separate relationship keys. — NS C3 and SM 2.2 need several pairs per relationship, and SR 2.5 says bindings never set interaction. Qualified ports make the stored shape independent of the open reply-binding decision (Q1).
- Properties use PL 9 verbatim: [[property]] with id, label, behavior, kind or template and predicate. Built-ins are explicit entries, and New project seeds deadlock-free and no-capacity-exceeded. Final predicates are [final] with combined/own. Entities in an array are identified by id or key. — PL A10 tells the format spec to adopt this shape. Array identity by field rather than by position keeps journal images and per-entity reload correct. ArrayOfTables insert, retain and no-op rendering were verified in toml_edit 0.25.17.
- The spec defines no predicate grammar of its own. It stores predicates verbatim and validates them with the PL/NS parser, including the NS L9 rule (E208). — A second grammar would accept or reject different texts than NS 5.3. The question of which places a predicate may name is left to NS OQ1 / PL OQ1.
- Place ports are never bound. L4 (unbound) applies only to transition ports and to state machine input/output events. A pair that names a place port, a state, an internal event or a non-port transition is notAPort (L5). — NS 6.2 and 16.1. The draft made every place port block lowering.
- State machines are stored as [state_machine] with initial and final, multi-line tables states.* (name), events.* (direction, name) and transitions.* (from, event, to, name). States, events and transitions share one namespace. — This carries the SM 1.1 content and makes SM-E04, E07, E09 and E11 reportable. Multi-line tables keep concurrent edits mergeable, and SM 1.5 leaves the syntax to the format spec.
- Scan attributes match SR 2.3–2.6 exactly: replicas and zones (1..1000), service (1..64), interaction (synchronous/asynchronous) and timeout (yes/no). An absent key means not stated, and out-of-range values are the warning badAttribute. owner, entry_point, logical_db and disabled_rules are removed. — The scan spec owns these. A typo in a scan attribute must not unload an element's behavior.
- Suppressions are a [[suppression]] array with key, disposition, reason and date, keyed by the SR 3.7 finding key. orphanSuppression is dropped in favor of the scan's display-time 'Suppressions without a finding'. — This is the SR 2.7 and 3.8 shape. The old RULE(id,…) key could not represent the level=, database= or defect= fields.
- Explicit LIM-2 limits apply. Byte limits are checked before parsing and count limits before decoding into the Model. Each one produces a named problem, never a truncation. — LIM-2 requires it, and the scan spec relies on load limits to bound its loops.
- Capacities, weights and initial counts are capped at 2^31−1 in files. An initial count above the capacity is a model problem (badInitial, L10) that does not stop the file from loading. — Predicate constants are i32 (PL E308), and NS rule 7 becomes unreachable from files. NS V29 expects the file to load.
- Temporary files are named .pn-<8hex>.tmp. A Windows rename is retried 5 times (about 0.6 s) and then reported as a failed write. The journal lock follows the TryLockError split: WouldBlock gives a read-only window, and Error gives a journal without a lock. The journal path is normalized before it is hashed. — This addresses MAX_PATH, Windows sharing violations and the case or verbatim-prefix aliasing of paths, and it keeps FMT-2 (every gesture journaled).
- The journal is versioned per file, and project migration steps are idempotent per file. Files touched by one project step are written together or not at all. — Lazy upgrade combined with partial Saves made the draft's project steps ill-defined.
- Applying a journal image removes the entity from any other file. A deleted element image deletes its file and every entity in it. — Reconnecting a relationship's source moves the entity between files, and replay must not leave orphaned entities or duplicates.
- The example fixture was regenerated in the final shapes. users is a container stand-in, fe1/map_entries and users/signed_in are place ports, the built-ins are explicit, and the suppression key matches a real finding. A block-variant golden was added. — The example must load with no problems and give the stated verdicts under the upstream rules. This was verified by a throwaway loader and an NS-rev-2 explorer: 330/21 and 24 markings, as in NS 13.2.

## Proposed glossary changes

- **Binding**: One pair of ports that a relationship connects: synchronous (the two transitions fire as one step) or asynchronous (messages wait in the relationship's generated place). A relationship holds zero or more bindings, at most one of them asynchronous. _Avoid_: Link, wire, connection, port mapping
- **Entity**: One stored thing that the tool saves, journals and compares as a whole: an element, its behavior model, a relationship with its bindings, a property, a final predicate, a layout entry or a suppression. Reload conflicts are reported per entity. _Avoid_: Record, object, item, row
- **Format version**: The integer `format` at the top of every project file. It says which version of the file format the file follows; older files are migrated when they are read and upgraded when they are saved. _Avoid_: Schema version, file version, project version
- **Recovery journal**: The app's own log of unsaved changes, kept in the app data folder and never in the project, from which those changes can be restored after a crash. _Avoid_: Autosave, backup, undo log, history
