# Reviews and disposition: Property language spec

Author: software architect. Final document: `docs/specs/property-language.md`.

## senior backend developer: reject

### Must fix
- Two normative definitions of the same language (draft §4, §6.2–6.4 vs net-semantics §5.1–5.3 and §11). The draft normalizes: `<` becomes `<= c-1`, NNF removes `not`, it has 4 relations, i64 weights, a postfix `Condition` and an infix canonical text such as `never api/ready + api/waiting != 3` and `no capacity exceeded`. Net semantics keeps the parsed predicate: `Not` stays, there are 6 cmps (lt…gt), i32 coefficients, i128 evaluation, and its canonical form is S-expression lines (`property never (atom ge 3 …)`, `property capacity-never-exceeded`). It also says explicitly that 'the parser does not rewrite `<` into `<=`'. The CheckKey bytes differ, and so do the explorer input types and the `holds` both crates must write. Pick one and state the other spec's amendment. Wherever it lands, the canonical property encoding must be produced by `net::encode` from the `NetProperty` (ADR 0009, ADR 0013 'computed by the worker from the net it explored'), not by `engine::lower` from the AST as §13 says.
- Overflow markings contradict net-semantics §4.4, §8.3, §9.3 and V34. The draft's §7 puts O ⊆ R, evaluates conditions on overflow markings and lets `never` be Disproved at one. Net semantics excludes O from R and does not evaluate p there. Its `recheck::replay` rule 3 requires 'M is in bounds and p(M)', so every Disproved the draft defines this way would end as Unknown InternalError. I confirmed this with a throwaway explorer on fixture N1. PL-13 (`never api-jobs >= 3`) is Disproved in 3 steps under the draft and Unknown CapacityExceededFirst under net semantics, the same situation as V34. PL-14 (`never api/ready = 0`) has length 3 under the draft, ending in the overflow marking (submit ×3), but length 4 under net semantics (submit, submit, take, submit). Reported marking counts also differ: N1 is '7 markings' in the draft but |R| = 6 plus |O| = 1 under net semantics. The template catalog §12.2(a) sides with the draft. This is one decision for the user, and both specs, the vectors and ADR 0016 must then say the same thing.
- Place references contradict net-semantics L9, §16.1 and §16.3. The draft lets a combined-scope condition name any child place (§5, ADR 0015 draft). Net semantics allows only place ports and generated places and fails anything else as ModelIncomplete `billing/inflight is not a port`. Under L9 most draft vectors (PL-14, PL-19, PL-21–27 name `api/ready`, `worker/busy`, which are not ports) would be Unknown ModelIncomplete, not the verdicts listed. The ADR 0015 rationale ('no binding rule exists for place ports, so the scope becomes model incomplete') is out of date: net-semantics §16.1 already exempts place ports from binding. Rewrite the rationale against the real alternative (place ports via L9) and route the choice to the user as one decision shared with net-semantics open question 1, research F1 and catalog §12.1.
- The grammar contradicts net-semantics §5.3 and its predicate vectors (§14.5). (a) The draft allows a leading unary minus (`sum = ["-"] term …`, PL-23). Net semantics requires `-1 * a/x >= 0` to be a parse error. (b) The draft rejects term-free comparisons (E301, PL-43). Net semantics keeps `a/x - a/x >= 0` and `3 = 3` as atoms with no terms. (c) The draft accepts only lowercase IDs that start with a letter (E103). The net-semantics slug is `[A-Za-z_][A-Za-z0-9_-]*`, so a valid ID like `Billing` or `_x` could never be referenced. (d) The `-` munch rules differ: the draft munches `-` only before an ID character, net semantics always does, so `x/p- 1` parses differently. (e) The draft reserves `capacity` and `initial`, which net-semantics §16.12 does not. There is one parser (`model`), so one spec must own the lexer and grammar, and the other must cite it.
- Integer limits conflict with `net::validate` (net-semantics §2.3 rule 6: coefficients and constants fit in i32). The draft allows constants up to 10^15 (§6.5). A property like `never x/p >= 3000000000` passes model validation and then fails net validation. Depending on where that happens, the result is ModelIncomplete or InternalError, never the verdict the user asked for. Make the two limit tables one table. Separately, folding `capacity()`/`initial()` can overflow i64 before E304 runs: `1000000000000000 * capacity(x)` with capacity up to 2^32-1 is about 4.3e24. Specify checked or i128 folding.
- The brief is not met for templates. §9 covers three UX §4.13 templates because 'the catalog was not included'. The final catalog has T1–T5, T7 and T8 with presets. Missing: T3 'Never overflows'. Missing: T4 'never fills up' (N = capacity − g, where g is the largest net add of one flattened transition). That needs a lowering rule, and the draft's text-only storage cannot express it as a value that follows edits. Missing: T7 presets 'its initial marking' (every place of the scope, which can exceed the 256-place limit) and 'done' (reference to the final predicate). Missing: T8. Missing: the catalog's preconditions and Unknown 'property does not apply' (not in the net-semantics §10.2 reason list). Also, T5's default K differs: the catalog uses initial(pool) + initial(held-by), the draft uses `initial(P)`. Storage is decided three different ways: the draft stores nothing and recognizes templates by shape, catalog §2.4 stores kind, version and params, research §6.1 stores tagged expanded properties. Expand every catalog template and preset, and escalate storage as one question.
- The evidence table (§8) is inconsistent with net-semantics §8.2 and §9.5. (a) It plans 'ILP infeasibility of the state equation per disjunct' as a later Proved technique for `never c`. Net semantics allows only the listed certificate kinds (a P-invariant bound, single atom with ge/gt and positive coefficients). The state equation M = M0 + C·σ does not hold on `drop` places because of clamping (the reason for net-semantics I2), so this certificate would give a wrong Proved on nets with drop places. Remove it or restrict it to nets without drop places and propose it as a §9.5 amendment. (b) It lists a siphon/trap certificate for deadlock-free, which net semantics does not have. (c) 'No capacity exceeded' is Proved only by exhaustion here, but net semantics has `Technique::Structural` when no overflow place exists (and catalog T2 forbids that shortcut). Align or escalate. (d) The draft proposes `Violation::Condition { values: Vec<i64> }`, net semantics has `Predicate { value: i128 }`. Pick one.
- §7 'Unknown capacity exceeded first names the first overflow place found' is ambiguous. Recheck replays this run (net-semantics §10.2), so the place must be defined: the smallest-ID exceeded place of the first overflow marking in BFS discovery order. Catalog §12.2(d) instead lists all of them. Two implementations that read 'first found' differently produce InternalDisagreement. Cite net-semantics §10.2, or state the rule.

### Should fix

Also cross-reference net-semantics open question 3 and catalog §12.3 (finals in slice 0 or 1) instead of fixing them at slice 4.

- Coordinate ADR numbers: the draft claims 0015 and 0016, while the catalog proposes a templates ADR and net semantics proposes several amendments. Allocate numbers once.

### Questions for the user
- Overflow markings and `never p`: should p be evaluated on an overflow marking? The draft and catalog §12.2(a) say yes: then 'never x/p >= 3' on an overflowing place is Disproved, as catalog T3 wants. Net semantics §8.3 and V34 say no: the same property is Unknown 'capacity exceeded first'. I can implement either from one text, but both explorers and every vector need a single rule.
- In a combined scope, may a property name a child's internal places (draft and catalog: any place), or only place ports and generated places (net-semantics L9, which needs promoting e.g. `control_plane/in_a` to a place port)?
- Should equivalent spellings share a CheckKey (normalize `>` to `>=`, remove `not`; draft and catalog), or should the predicate be hashed as parsed (net semantics: fewer transformations in the unchecked lowering path, but `p > 50` and `p >= 51` get different keys)?
- How are templates stored? Options: nothing stored, recognized by the shape of the text (draft); kind ID, version and parameters, expanded at lowering (catalog); or expanded properties tagged with a template ID (research). Only the second lets 'never fills up' (capacity − g) and T7 'done' follow later model edits.
- Is 'no capacity exceeded' on a net with no overflow place Proved structurally, naming the drop places (net semantics), or always by exploration (catalog T2, draft)?
- Should failed template preconditions (T3 on a place that blocks, T4 decided by when_full alone, T5 with an empty pool) be a new Unknown reason 'property does not apply' (catalog), ModelIncomplete (fits net-semantics §10.2 'no other reasons'), or only a warning (draft W503)?

## researcher: reject

### Must fix
- Conflicts with the final net semantics spec's concrete syntax (net §5.3, §14.5), which already defines what `model` parses in slice 4. The draft never cites that spec, so the project would end up with two grammars. Specific conflicts: (a) net §5.3 accepts `==`, but draft E102 rejects it (PL-33). (b) Net §5.3 has no unary minus, and its vector `-1 * a/x >= 0` is a parse error; draft §4 `sum = ["-"] term` accepts it (PL-23). (c) The draft allows `operand * INTEGER`; net §5.3 allows only `INT '*' ID`. (d) Lexing of `-` differs. In net §5.3 any `-` right after an ID character joins the ID, so `x/p- 1` lexes as ID `x/p-`. In draft §3.1 the `-` joins only when an ID character follows it. (e) Net §5.3 keeps comparisons whose terms all cancel (`a/x - a/x >= 0` and `3 = 3` are valid and true); draft E301 rejects them (PL-43). (f) Net §2.2 slugs are `[A-Za-z_][A-Za-z0-9_-]*`, but draft E103 rejects uppercase and a leading `_`. The slice 4 acceptance text writes `Billing/inflight`. (g) The reserved words differ: the draft adds `capacity` and `initial`. (h) Net §5.3 says the parser does NOT rewrite `<` to `<=`, while draft §6.2 step 3 does. Fix: either adopt net §5.3, or make this spec the owner of the concrete syntax and list the change to net §5.3 and §14.5 as an explicit proposed amendment, with the vectors updated in both.
- There are two canonical forms for the CheckKey. Draft §6.3 hashes infix text (`never api/ready + api/waiting != 3`). Net §11 defines `canonical_property` as `property never <pred>`, with the S-expression `(atom <cmp> <const> <id> <coef> …)` and kind names such as `capacity-never-exceeded`. Template catalog §2.4 describes a third form (`Σ w·p ≥ c`). ADR 0013's fitness and invariance tests need exactly one byte-level definition. The draft must use net §11 or amend it explicitly. The draft's own ordering rule is also ambiguous: §6.2 step 6 sorts children by 'printed form', and it does not say whether a nested group is sorted with or without its parentheses. The example `(api-jobs = 2 …) or api/waiting >= 4` works only if they are included. That is a CheckKey determinism hole.
- The `net::NetProperty` types contradict net §5.1, §2.3 rule 6 and §9.1. The draft uses `Condition { atoms, postfix program }` with 4 relations, i64 weights and constants up to 10^15 (§6.4, §6.5). Net §5.1 has a `Pred` tree with 6 comparison operators. Net §2.3 rule 6 requires coefficients and constants to fit in i32, and both explorers re-validate on entry. So a draft-valid property such as `never x/p >= 3000000000`, or a folded `capacity()` sum above 2^31 − 1, fails `net::validate` in the worker and ends as Unknown InternalError. The draft's `Violation::Condition { values: Vec<i64> }` also replaces net's `Violation::Predicate { value: i128 }`. Pick one set of types and limits, and list the changes to net §5.1, §2.3 rule 6, §9.1 and design §3 as amendments.
- The overflow semantics of `never` contradict net §8.3 and V34. Draft §7 evaluates conditions on overflow markings, and its R includes O. Net §8.3 says p is not evaluated on overflow markings, and its R excludes O, as does the proposed glossary entry 'Reachable marking'. I recomputed the draft's own fixture N1 with a BFS in canonical transition order (scratch script, not in the repo). Under net §8.3, PL-13 (`never api-jobs >= 3`) is Unknown 'capacity exceeded first', not Disproved in 3 steps. PL-14 (`never api/ready = 0`) is Disproved in 4 steps (submit, submit, take, submit), ending in the in-bounds marking ready = 0, jobs = 2, busy = 1, not in 3 steps at the overflow marking. ADR 0009 requires both explorers to be written from one text, so two texts give diverging golden tests or InternalDisagreement. The marking count convention also conflicts: draft §14 counts include overflow markings, but net §4.4 reports |R| only, and agreement in §9.4 compares counts. Template catalog §12.2(a) and T3 depend on the draft's reading. Under net §8.3, T3 `never p > capacity(p)` can never be Disproved, which is exactly V34. Resolve this in one place, escalate it to the user, and fix the vectors on whichever side loses: PL-13 and PL-14, or V34 and V35.
- The brief is not met for templates. It requires the expansion of every template in the catalog, but the draft says the catalog was missing and uses only the three templates of flows.md §4.13. It now has to cover T1 (deadlock-free with the scope's done when), T2, T3 (`never p > capacity(p)`, which depends on the previous item), T4 with its presets, T5, T7 with its presets, T8, and the catalog §6 preconditions. T4 has 'at most N in flight' and 'never fills up' (N = capacity − g, where g is the largest net number of tokens any single step adds to the place). T5's default K is the initial tokens of the pool PLUS the held-by places. The draft uses `initial(P)` only, which asks a different question when held-by places start non-empty: with pool 2 and held 1, the draft asks held ≥ 2 and the catalog asks held ≥ 3. T7 has 'its initial marking' (every place of the scope at its initial count, generated places at 0) and 'done'. The catalog §6 preconditions end in Unknown 'property does not apply', a reason that does not exist in net §10.2's closed enumeration of Unknown reasons. Reconcile this with the draft's choice to map everything to ModelIncomplete.
- Template storage decides something the template catalog escalated. Draft §9 says 'templates store nothing' and the dialog recognizes a template from the shape of its condition. Catalog §2.4 and §12.5 propose storing a kind ID, a version and the parameters, expanded during lowering, with W10 'capacity 50 then, 30 now' and a format migration whenever an expansion rule changes. The research (§6.1, open question 4) proposes expanded properties with a template tag. The TOML shape in §10 depends on this choice, so the draft must present the options and stop asserting one as decided.
- Place references (§5.3, draft ADR 0015) argue against an outdated premise. The rationale says that promoting places to ports 'does not help, because ADR 0010 requires every port to be bound'. Net §16.1 already proposes amending ADR 0010 so that only transition ports must be bound. Net L9 and §16.3 then restrict properties to place ports and generated places, while catalog §12.1 proposes the opposite. The user currently gets two contradictory recommendations from two specs. The draft must cite net L9 and open question 1, restate the trade-off against the place-port option, and say that accepting ADR 0015 drops L9. The PL vectors and §5.2 rule 1 must also state which variant they assume.
- The evidence table (§8) diverges from net §8.2 and §9.5, and one entry in it is unsound. (a) It lacks the structural Proved for 'no capacity exceeded' (`Technique::Structural`, markings 0, recheck inspects its own composition). So PL-18 ('Proved, 6 markings' on N2, which has no overflow place) contradicts net, which gives Proved (structural). Catalog T2 says 'no shortcut', so this conflict must be escalated (net open question 8). (b) It lists 'ILP infeasibility of the state equation per disjunct' as a future Proved technique for `never c`. The state equation M = M0 + C·x is a necessary condition for reachability only under the ordinary firing rule (Murata, Proc. IEEE 77(4), 1989, the matrix-equation section). On a `drop` place, clamping discards tokens, so reachable markings need not satisfy it, and an 'infeasible' ILP can certify a property that is false: a wrong Proved. Net §9.5 already limits certificates to P-invariants with y(p) = 0 on drop places, for a single atom with non-negative coefficients and ge or gt, and requires an amendment before any new kind is added. Remove the entry, or restrict it the same way. Siphon/trap for deadlock-free is likewise not specified in net §9.5. (c) 'Names the first overflow place found' must use net §10.2's definition: the smallest-ID exceeded place of the first overflow marking in discovery order.

### Questions for the user

- Should 'no capacity exceeded' on a scope without any `overflow` place be Proved structurally, naming the drop places (net semantics §8.2, open question 8)? Or should it always be explored and re-checked (catalog T2)?

## Decisions

- Net semantics §5.3 owns the predicate lexer, grammar and atom normalization. This spec transcribes it as EBNF, adds only the property-kind prefix, error messages and limits, and withdraws revision 1's grammar. — There is one parser in `model`, and two normative grammars would give two sets of golden tests. Every review flagged this. Accepting `==`, upper case and term-free atoms, and rejecting unary minus and `ID * INT`, keeps the net semantics §14.5 vectors valid.
- The canonical property line and the CheckKey come only from `net::encode::canonical_property` as defined in net semantics §11. This spec defines no second canonical form, and the parsed tree is not rewritten: no `<` to `<=`, no NNF, no flattening. — ADR 0009 and ADR 0013 require one byte-level form, produced by the worker. Each rewrite is unchecked shared-lowering code. Equivalent spellings sharing a key is escalated as OQ3.
- `NetProperty` uses net semantics §5.1 `Pred` with i32 coefficients and constants, i128 evaluation and six comparison operators. Revision 1's `Condition`, its postfix program, i64 and the 10^15 limits are withdrawn. — A property that is valid in the model must not fail `net::validate` (net semantics §2.3 rule 6) in the worker and end as InternalError.
- The `capacity()` and `initial()` functions are removed from the hand-written predicate language. Values that should follow model edits live only in template parameters, which are expanded at lowering. — It keeps a single grammar shared with net semantics, needs no reserved words beyond and/or/not, and removes the folding-overflow hole.
- The evidence table cites net semantics §8 and §9: structural Proved for no capacity exceeded, and certificates only as in §9.5. The ILP state-equation and siphon/trap entries are removed. — The state equation does not hold on drop places, so it could produce a wrong Proved. Neither technique is a certificate kind of net semantics §9.5.
- The vectors follow net semantics §8.3 as written (p is not evaluated on overflow markings). A separate table lists every vector that flips if the user chooses evaluation (OQ2). — Net semantics is the final normative text until it is amended. Showing both outcomes lets either rule be implemented without new computation.
- Resolution follows net semantics L9 while it is in force, with E208 as its user-facing message. Fixtures declare every named place a place port, so the vectors hold under both outcomes of OQ1. Revision 1's argument that place ports "do not help" is withdrawn. — Net semantics §16.1 already exempts place ports from binding. The user should get one recommendation from both specs (L9).
- The resolution order is defined, and every reference is reported with exactly one error. Scope membership is checked before the name. — It makes the error vectors deterministic (E-25, E-26), which the backend developer asked for.
- Every template and preset in the catalog is expanded into an exact Pred with a fixed form. T5's default K is initial(pool) plus the initial tokens of the held-by places. 'Never fills up' uses g, the largest net add of one step of the flattened net. T3 ships only if OQ2 chooses evaluation. — The brief requires every catalog template. The catalog defines K. Under net semantics §8.3, T3 can never be Disproved and duplicates T2.
- Template expansions must round-trip through their rendered Checks line: parse(render(E)) == E. — This makes 'edit as predicate' exact and gives one golden property for the unchecked lowering path.
- The headline is generated from the template or the checked NetProperty. A free-text `label` is secondary only. — A stale user name over an edited predicate could make a Proved read as more than it says (product manager must-fix).
- The TOML keys are `behavior` (own or combined; not `scope`), `predicate` (not `condition`) and `label` (not `name`). `kind` and `template` are mutually exclusive. Unknown keys are kept and reported. Limits are 256 properties per element and 4,096 per project. — Glossary: scope is the element. ADR 0003 calls it a predicate, and the E5 files use `predicate`. FMT-1 forbids dropping unknown fields, and LIM-1 requires bounds.
- Final predicates use a `[final]` table with `own` and `combined` keys and travel as OpenNets.final (net semantics §6.1). The `final` key inside a property entry is reserved. — It is consistent with net semantics. The shape also survives the per-property override (OQ7) and the slice move (OQ8).
- 'Capacity exceeded first' names the smallest-ID exceeded place of the first overflow marking in discovery order (net semantics §10.2). Counterexamples are definite under net semantics §12. — Under 'first found' or 'every place', verify and recheck could disagree.
- `Violation::Predicate { value: i128 }` is kept. Its value is the left-hand sum of the first atom in pre-order, informational only, and carried as a string in the DTO. — It matches net semantics §9.1 and §9.3 and satisfies IPC-2 for values above 2^53.
- The slug generator never reissues an ID that a property, final predicate or template parameter still references. — It prevents silent retargeting of a dangling property to a new place (research should-fix).
- State references use `element/state`, with a load error when a state and an event of one element share a name. The `:` prefix is not used. — It follows net semantics §2.2's single namespace and needs no new qualified-ID shape. The rule is offered to the format owner as OQ13.
- Terminology: 'predicate' and 'final predicate', with 'done when' as the UI label only. 'Condition', 'final condition' and 'scope kind' are withdrawn. — CLAUDE.md requires glossary terms exactly, and three names for one concept confuse users.
- No ADR numbers are claimed. Three ADR drafts are provided without numbers. — Net semantics, the catalog and this spec all propose ADRs, so the user allocates numbers once.
- The differential corpus for user properties uses only nets whose places all block, encoded with complement places per net semantics OQ10. — TAPAAL would explore past overflow markings, and plain PNML cannot express drop.

## Proposed glossary changes

- **Linear marking predicate**: A statement about one marking: sums of token counts with whole-number weights, compared with whole numbers and combined with and, or and not, for example `billing/inflight + shipping/inflight > 2`. Short form: predicate. User properties and final predicates are written as predicates. _Avoid_: Condition, formula, query, expression, constraint, guard
- **Final predicate**: The predicate of a scope that says which markings count as proper termination. The UI calls it "done when". A marking without enabled transitions that satisfies it is not a deadlock. _Avoid_: Final condition, final state, goal, accept condition, done condition
- **Own scope / combined scope**: The two kinds of behavior a property of a scope element can be about. Own scope: the element's own behavior model, with its ports firing freely. Combined scope: the behavior of the children in its view, combined through their bindings. The file stores this as `behavior = "own" | "combined"`. _Avoid_: Scope kind, local scope, system scope, level scope
- **Property template**: A named sentence with blanks, for example "Never holds the whole pool". Filled in, it expands to exactly one property. The tool expands it again from the current model at every check, so values such as a capacity follow edits. _Avoid_: Pattern, query, formula, macro, preset (a preset is one fixed choice inside a template)
- **Disproved**: The property does not hold. The tool has either a counterexample that shows it or, for no dead transitions, an exhaustive exploration that the second explorer confirmed. _Avoid_: Refuted, failed, violated
