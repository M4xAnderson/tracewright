# Reviews and disposition: Property patterns research

Author: researcher. Final document: `docs/research/property-patterns.md`.

## software architect: approve-with-changes

### Must fix
- Fairness claim is wrong where it matters most (§0 Summary bullet 1, §3.1 Existence and Response rows, §3.3 Termination and Response rows). The draft says `always reachable` equals "eventually, under a strong fairness assumption". Strong fairness on Petri net transitions is not enough. Counterexample: a token moves between L and R through l2r/r2l, and a flag toggles through set/unset; p = (L=1 and flag=1). The reachability graph is strongly connected, so AG EF p holds. Yet the cycle (L,0) -l2r-> (R,0) -set-> (R,1) -unset-> (R,0) -r2l-> (L,0) fires every transition infinitely often and never reaches p. §4's own definition (fairness on edges of the global reachability graph) is the correct one, so use it everywhere. Second error: under edge-fairness, AG EF p means "p infinitely often, or at the end" (recurrence, AG AF p). It does not mean Existence (AF p). It is a sufficient but strictly stronger stand-in: a design where p happens once and is then never reachable again is Disproved even though "p eventually happens" holds. The Existence row must say "stronger than", not "=". The verdict-panel sentence "assumes every possible step is eventually taken" should become something like "assumes that in any situation that keeps recurring, every step possible there is eventually taken; says nothing about load".
- §0 Summary bullet 4, §3.3 Election safety row and §6.1 T3 are wrong to call `never primaries >= 2` the "counting shadow" of election safety. The property the draft itself quotes from MongoDB, "not both primary with the same term", allows two primaries in different terms, and correct Raft/MongoDB protocols reach such states (a stale primary). The counting predicate is strictly stronger, so it would be Disproved on a correct protocol, and the draft presents that as the published property. Either drop the claim or state that the shadow is a stronger property that correct protocols violate. Then remove "abstracted Raft/MongoDB election safety" from T3's justification.
- Templates expand into several properties (T2, T5, and the UpperBounds template), but the draft never says how many verdicts the user sees or how a template is stored. GLOSSARY defines one check per property ending in exactly one verdict, and ADR 0001 makes the file format durable data. If a template shows one combined status, it needs a stated rule: Disproved if any part is Disproved, else Unknown if any part is Unknown or not current, and Proved only if every part is Proved and current. Without that rule the UI can show a Proved over an Unknown part, which is a wrong Proved in the user's mind. Persistence is also a format decision that is expensive to reverse: either store the expanded properties with a `template` tag, or store templates as their own entity. Pick one, or list it as an open question for an ADR.
- T5 "Finishes cleanly" (§6.1, §3.2 proper-completion row) gives misleading Disproveds on the models this tool actually targets. `never (done >= 1 and Σ leftovers > 0)` is van der Aalst's single-case (1-sound) notion. With folded populations (E5 uses pending = 2, 3 or 5 everywhere), one case finishing while others are still running violates it. Resource places such as threads_free, lock or buf_free hold tokens at the end by design, so "Σ leftovers" over all other places fails too. Specify `done = N` (N cases from the initial marking), state the k-case assumption, and define leftovers as non-resource places, or resource places measured against their initial counts. `always reachable done` must then mean the full final condition, not `done >= 1`.
- F4 "can reach p" breaks more than the Counterexample term. GLOSSARY Proved means "holds for every possible behavior", but EF p is existential. GLOSSARY Disproved means "has a counterexample", but EF p's Disproved is exhaustive. ADR 0008 allows only two kinds of evidence for Proved (a certificate, or agreement of the second explorer), and a replayed witness is a third kind, so ADR 0008 and 0010 both need amending, not only 0003 and 0010. The "glossary changes" section that F4 points to does not exist in the draft. Also state the ADR 0014 interaction: a witness must not pass through an overflow marking, and an exhaustive "not reachable" with an overflow marking reachable is Unknown "capacity exceeded first". Present the cheaper alternative too: an "expected: reachable" polarity on `never p`, which shows a Disproved as the expected outcome without changing any verdict semantics.
- F1 is labeled "Proposed ADR 0003 clarification", but it is an amendment that reverses an explicit choice. ADR 0003 says properties refer to `element/port` IDs. ADR 0002 rejected references into another element's net because renames would break other files and rule out later contract abstraction. Option (a) brings both costs back for properties: a parent-file property that names `child/internal_place` stops working when the child's net is replaced by a contract. Name it a proposed amendment of ADR 0003, record that consequence, and note that slice 4's own acceptance criterion (`Billing/inflight + Shipping/inflight > 2`) depends on the outcome. Also fix the attribution: slice 4's example is not in the E5 files. Only E5 case 1 shows that internal places are needed (its toml marks only transitions as ports).
- Part of the brief is missing: "common TLA+/Quint/P invariants in published specs" and "Alloy assertions". §2.3 describes the P monitor mechanism, the Quint CLI flags and Alloy 6 features, but samples no invariants or assertions from published P, Quint or Alloy specs. Possible sources: the P tutorial and case-study specs such as two-phase commit atomicity and progress monitors, the Quint examples repository, and published Alloy models. Add a small sample with citations and classify each item like §3.3, or state explicitly that it is not covered and why.

### Should fix
- Deadlock-free paired with `always reachable` is redundant: §3.1 Existence and Response rows, §3.3 Termination, §6.1 T2. AG EF F already forces every dead marking to satisfy F, because a dead marking can reach only itself. Dropping the pairing also removes T2's hidden dependency on per-property finals (F3). As written, §6.1's "no ADR change beyond F1 and F2" is inconsistent with T2, which needs F3 whenever F differs from the scope's final predicate.
- The Response-on-anonymous-tokens argument (§4) assumes that every exit from `pending` means "answered". Under ADR 0014 a `drop` on `pending` discards tokens, and timeout or discard transitions also empty it. Without a restriction, `always reachable pending = 0` can be Proved for a design that sheds every request. The template must name the answered transitions, or reject `drop` and other non-answer exits on `pending`.
- The LoLA causal-precedence trick in §3.1 contradicts F6. A one-token place consumed as a pre place of S disables S after its first firing, which changes the behavior. Combined with ADR 0014's global overflow rule, that change can turn Unknown "capacity exceeded first" into Proved. Use a non-blocking history place instead (S puts a token into `s_done` with capacity 1 and `drop`) and cite the LoLA trick only as background.
- The probability-1 claim in §4 needs scheduler probabilities bounded away from zero, for example a fixed positive probability per marking and step (a finite Markov chain). A history-dependent scheduler with decaying probabilities breaks it.
- The baseline table in §1 omits the ADR 0014 rule that changes every row except no capacity exceeded. When an overflow marking is reachable and no violation is found, the result is Unknown "capacity exceeded first", and generated places overflow by default. Add a column or note, and say in §6.1 that T1–T6 on models with default generated places will often end Unknown until the user picks `block` or `drop`. Also flag the open semantic question for no dead transitions: does a transition count as enabled in an overflow marking?
- L2 "smallest safe bound" (§6.2) answers J4 only for `overflow` places, where behavior below the capacity is the same as with no capacity. For `block` and `drop` places the bound is at most the capacity by construction, and lowering the capacity changes the behavior, so J4 there means re-checking deadlock-free or shedding over several capacities (different nets, different CheckKeys). Say so, and mention binary search over k.
- F4's vacuity argument cites the wrong example. In E5 case 1 with a timeout the model moves freely, and the Proveds come from abstracting time away, not from vacuity. A "can reach" check would not have caught it. Use real vacuity cases instead, such as a dead initial marking or a branch that never fires, and note that no dead transitions already partly guards against them.
- F5 needs more precision. `Enabled(element/port)` names no transition of the composed net, because fused transitions have `relationship/caller+callee` IDs. Define the atom as the disjunction over composed transitions whose constituents include t, computed by `verify` and `recheck` from their own compositions, with `net` storing data only (ADR 0009) and a canonical encoding for the CheckKey (ADR 0013). Also note that the "Template" rows built on `enabled(t)` in a combined scope need F1, because the pre places of a port transition are internal.
- F3 should spell out the structural consequence. design.md puts `finals` on `Net`, so the flat-net encoding, and with it the CheckKey of every property in the scope (including `never p`), changes when finals change. Moving finals into `NetProperty::DeadlockFree(final)` fixes that spurious staleness and fits ADR 0013's invariance tests. Recommend it explicitly and list the design.md and type change.
- Glossary hygiene. Dwyer's "scope" (Before R, After Q, ...) clashes with GLOSSARY's scope (the element); call it "pattern interval" or similar. "Pattern" clashes with the pattern library (the draft already notes this). "Invariant" is a listed Avoid term for Property in the tool's own wording. "Liveness" is overloaded: L4 liveness of a transition versus a liveness property. "Template" and "observer" are new terms with no proposed glossary entries. Add the missing glossary-changes section.
- T4's name, "Fair share of a pool", does not match its expansion, which says one caller never holds the whole pool, and §0 calls it "share of a pool". Use E5's "share of a resource" wording consistently.
- Reproducibility of §2.2. The liveness regex ends in "…", so nobody can rerun it. Publish the exact patterns and the commit hash. My rerun on a fresh shallow clone with my own regex found 245 .cfg files, 213 with INVARIANT(S), 99 with PROPERTY/PROPERTIES, 58 with CHECK_DEADLOCK FALSE, TypeOK 112 and TypeInvariant 34. My liveness-name match gave 43 and refine/spec gave 24, against the draft's 46 and 22. That is close but not identical, so the figures need the exact method next to them.
- Some claims are neither cited nor labeled. "Typically because proper termination is not a deadlock" (the CHECK_DEADLOCK interpretation) and "type invariants have no counterpart in a P/T net" are the author's own inferences; mark them **[own derivation]** or cite a source. Spec authors also turn off deadlock checking for open specs whose terminal states are intended.
- Option (c) for F1 is missing. A property over a child's internal places can live in the child's own scope. For children whose ports are only transitions, the own scope (closed ports fire alone) over-approximates the combined behavior projected onto that child's places, so a `never p` that is Proved there also holds when combined. This is not true when a child has place ports. It would cover E5 case 1's share-of-pool predicate without breaking encapsulation. Evaluate it next to options (a) and (b).

### Questions for the user
- F1: should properties be allowed to name a child's internal places (`element/place`)? This amends ADR 0003 and weakens ADR 0002's encapsulation for later contract abstraction. The alternatives are an "observable" place port that is exempt from ADR 0010's must-be-bound rule, or keeping such properties in the child's own scope. Slice 4's acceptance example depends on the answer.
- Should "can reach p" ship in slice 4? It needs glossary changes to Proved, Disproved and Evidence plus ADR 0008/0010 amendments. The alternative is an "expected: reachable" marker on `never p` that adds no new verdict semantics.
- Should a property template be stored in the project files as its own entity, or only as tagged expanded properties? It is a file-format decision that is costly to reverse (ADR 0001), and it decides whether the UI shows one combined verdict or one verdict per expanded property.

## product manager: approve-with-changes

### Must fix
- Wrong equivalence for Existence (§0 bullet 1, §3.1 Existence row, Decisions claimed #2). The draft says `always reachable P` 'equals' AF P / 'eventually' under strong fairness. Your own §4 proof shows something stronger: under edge-fairness, AG EF P means 'P infinitely often, or the run ends dead in P'. That implies AF P, but AF P does not imply it: a P that holds once and is never seen again satisfies AF P and fails AG EF P. Replace 'equals' with 'is a sufficient, stronger stand-in'. Then say in §3.1 that a transient P (for example 'eventually initialized') gets a Disproved that does not answer the user's question.
- Two template names read as more than they prove (§6.1), against E5 implication 5 and the decided north-star non-goal. (1) T5 'Finishes cleanly' is a 'will' wording built on `always reachable done`, which the draft itself forbids in §4. Rename it to something like 'Can always finish cleanly'. (2) T4 'Fair share of a pool' says 'fair', which reads as scheduling fairness or freedom from starvation, and §3.3 and §6.3 exclude both. Rename it to 'Never holds the whole pool' or 'Share of a pool' (the §0 summary already uses 'share of a pool').
- T5 proper completion is wrong for folded populations (§3.2 'proper completion' row, §6.1 T5). `never (done >= 1 and Σ leftovers > 0)` is the single-case workflow-net form. In E5-style models with N folded cases (for example `pending = {init = 3}`), `done >= 1` holds while other cases are still running normally, so every such design gets a false Disproved. The template must use `done = N` (N from the initial marking) or state the single-case precondition.
- The §6.1 claim 'None needs an ADR change beyond F1 and F2' is false, and Decisions claimed #1 ('without new semantics') hides the dependency. T2 and T5 pair `always reachable F` with deadlock-free using F as the final predicate. Two such templates in one scope need different finals, and ADR 0003 makes final markings model data with one predicate per scope (design.md §3 `Net { finals: Option<FinalPredicate> }`). So T2 and T5 depend on F3, a deviation from a settled decision. F3 must be labeled a proposed ADR 0003 amendment, not a 'recommendation'. F1 is likewise an amendment to ADR 0003's 'element/port' rule, not a 'clarification'. Slice 4 cannot be specced until both are decided.
- F1 misses generated places. The north-star example question ('can the queue between Order API and Billing exceed 50?') names a generated place, whose qualified ID is the relationship (ADR 0010 Semantics), not `element/port`. F1 option (a) must cover `relationship` IDs as well as `element/place`. It must also say whether a state machine state can be named (slice 2 compiles states to places), for example `Breaker/open = 1`.
- The observer encoding contradicts ADR 0014 (§5 F6, and the Model edit rows in §3.1 for Bounded Existence (event) and Precedence). An `overflow` observer place at k+1 would make every other property Unknown 'capacity exceeded first'. It would also turn the user's 'no capacity exceeded' into a Disproved on a phantom place. Use `drop` with capacity k+1: the count saturates, the observed transition is never blocked, and the property is `never count >= k+1`. Each Model edit instruction must also say which `when_full` the added place uses, because ADR 0014 requires every place inside a behavior model to choose one.
- F4 'can reach p' conflicts with the glossary definition of Proved, and the draft does not say so. GLOSSARY.md defines Proved as 'holds for every possible behavior of the model'. A Proved `EF p` means 'some behavior reaches p', which is exactly the kind of Proved that reads as more than it is (a user sees 'Proved: can reach done' and reads 'always reaches done'). The proposal must name the glossary changes it needs: Proved, Evidence ('a replayed counterexample'), Replay ('stepping through a counterexample'), and the Relationships line 'Only a Disproved verdict has a counterexample'. It must propose the new term for the positive sequence explicitly, and that term must not be 'witness' or 'trace', both of which the glossary lists under Avoid. Otherwise it must present a wording in which the verdict stays universal.
- Part of the brief is missing (§2.3). The brief asks for common invariants in published TLA+/Quint/P specs and for Alloy assertions. For P the draft cites only the manual and the abstract of a 2025 article. For Quint it cites only the CLI docs, with no published spec. For Alloy it has no assertions at all, only tool documentation. Either survey a few published P, Quint and Alloy specs (for example the P tutorial and case-study specs, the Quint examples repository, and Alloy models from published papers) and add their properties to §3.3, or list this explicitly in §8 as a gap with its reason.

### Should fix
- Simplify the slice-4 template set (§6.1). T1 (`never Σ > k`), T3 (`never Σ critical >= 2`) and T4 (`never Σ held_by_X >= c`) are the same form with different wording. Present them as one template ('At most k at once') with named presets (mutual exclusion is k = 1; pool share is k = pool − 1). T6 ('Nothing leaks') rests on the verification.md catalog, not on a user problem or E5, so move it to 'after v1, on journal evidence'. A smaller set keeps slice 4 thin and still covers both slice-4 acceptance examples and the decisive E5 predicate.
- Rename L2 'Smallest safe bound' and correct its meaning (§3.2 UpperBounds row, §6.2 L2). 'Bound' is listed under Avoid for Capacity in GLOSSARY.md; use 'capacity'. More importantly, the largest count that occurs only gives the smallest capacity with identical behavior. J4 asks whether a smaller capacity is still safe, and for a `block` or `drop` place that capacity changes behavior (more blocking, more shedding), so the user's properties must be checked again at each candidate capacity. Also state that the derived number may be shown only if every check behind it was decisive. If any check ends Unknown, the result is Unknown, never a number.
- The §5.1 'Response on anonymous tokens' argument depends on a modeling precondition the tool cannot check: that leaving `pending` means 'answered'. A timeout or a `drop` that removes tokens from `pending` (the E5 case 1 timeout) makes `always reachable pending = 0` come out Proved while requests go unanswered. That is a wrong Proved in the user's mind. The T2 template text should state this precondition, and the E5 lesson 'slow = never responds' should be linked from T2.
- Make the verdict wording for always reachable literal (§4 'Why the wording matters'). The proposed line 'assumes every possible step is eventually taken' frames the Proved as an 'eventually' claim with a side assumption, which invites the 'will' reading. Lead with what was proved ('from every reachable state, idle can be reached') and follow with 'does not mean it will be reached, especially under load'.
- F1 option (a) has a second cost that the draft does not mention. ADR 0002 rejected binding to element internals because of renames and because it would 'rule out later contract abstraction'. Parent properties over child internals would block that abstraction in the same way. Also note a silent-retarget risk: if an internal place is renamed and another place later takes the old name, the property quietly refers to the wrong place, and a Proved about it is wrong in the user's mind. Recommend that the rename command update property references in the same gesture.
- F4 offers only one way to prevent vacuous Proveds. Add at least two cheaper candidates: run 'no dead transitions' by default next to every user property in a scope, and show the reachable-marking count and any transition never enabled in the Proved panel. Then compare all three before pulling 'can reach p' into slice 4.
- §3.1 mislabels Dwyer Bounded Existence. Dwyer's Bounded Existence counts occurrences of P along a run, while 'at most k at once' (`AG Σ <= k`) is Universality over a counting predicate. Relabel the row so it does not overstate coverage of Dwyer patterns, and move the Cosmos 'at once' example to the Universality row.
- Add 'property template' to GLOSSARY.md as an explicit proposed entry, with Avoid: pattern, query, formula (Decisions claimed #6). Define the levels 'Partial' and 'N/A' used in §3.3, or replace them with levels from the §1 level table. The §3.3 'No load shed' row says Template but §6.2 L3 puts it after v1 with F5; make the two consistent.
- Mark the remaining own derivations and uncited claims. §2.2 says configs turn deadlock checking off 'typically because proper termination is not a deadlock', which is an interpretation and should carry [own derivation]. §0 calls 46 of 243 configs (19 %) a 'large liveness share'; say 'a substantial minority' or give the percentage. §3.2 says 'LoLA recommends one transition per run for memory' with no citation.
- State the ranking criterion in §6.1. The Dwyer frequencies come from 1999 finite-state verification users, while the target user (north-star.md) is a solo backend designer. The only evidence from this tool's own setting is E5, so say how the two sources were weighed. Also add the rule for keeping or cutting templates after dogfooding, for example the share of journal questions stated through a template versus a raw predicate, and whether I1 (time to first verdict) improves.

### Questions for the user
- Before the slice 4 spec, there are two ways to let properties see more than ports, and both amend ADR 0003. Option (a): properties may name any internal place (`element/place`), generated places (relationship ID) and state machine states, accepting that the parent depends on the child's internals. Option (b): properties may name only a new 'observable place' port that does not have to be bound. E5's decisive pool-share predicate needs one of the two. Which do you want?
- May a property override the scope's final predicate, as E5 did? That means amending ADR 0003's 'initial and final markings are model data'. The alternative is to allow only one final predicate per scope, which limits the 'can always finish' templates to one per scope.
- Should 'can reach p' (EF p) come into slice 4 as a guard against vacuous Proveds, even though it requires changing the glossary meaning of Proved ('holds for every possible behavior')? Or should slice 4 instead always pair user properties with 'no dead transitions' and show reachable-state counts, leaving EF p for later?

## Decisions

- `always reachable p` is presented as a sufficient, strictly stronger stand-in for Existence and Response under edge-fairness (fairness on edges of the reachability graph), never as an equivalent, and never under strong transition fairness. — Both reviewers' counterexample holds: a fair cycle that fires every transition misses p. Under edge-fairness AG EF p means recurrence (GF p or ends in p), which implies AF p but not the reverse.
- The draft's 'counting shadow' of election safety ('never primaries >= 2') is classified as 'Stronger only' and removed from the mutual-exclusion justification. — MongoDB and P Raft state the property per term; correct protocols reach states with a stale primary in an older term.
- Templates do not pair deadlock-free with `always reachable F`. — AG EF F already forces every dead reachable marking to satisfy F. Dropping the pairing removes the templates' dependency on per-property finals (F3).
- The slice 4 template set is reduced to three: At most k at once (with Mutual exclusion and Never holds the whole pool as variants), Can always get back to / finish / clear pending, and Can always finish cleanly (k-case soundness). Nothing leaks moves after v1. — Three draft templates were the same `never Σ > k` form. Conservation has no E5 or user-problem evidence. A smaller set keeps slice 4 thin.
- Proper completion uses `done = N` with N cases from the initial marking, and resource places are measured against their initial counts. — The single-case form `done >= 1` gives false Disproveds on folded populations such as E5's, and resource places hold tokens at the end by design.
- Each expanded property keeps its own verdict. A template group shows a derived summary: Disproved if any part is Disproved, else Unknown if any part is Unknown, stale or unchecked, and Proved only if every part is Proved and current. — This keeps one verdict per check (GLOSSARY.md) and prevents a Proved summary from hiding an Unknown part.
- Observer and history places use `when_full = drop` with capacity k+1, take only a post arc, and are never pre places of the observed transition. — An `overflow` observer makes other properties Unknown and creates phantom capacity violations (ADR 0014). LoLA's one-token pre place changes the behavior the other properties see.
- The F4 vacuity guard ships in slice 4 as no dead transitions next to user properties, plus exploration counts in the Proved panel. 'Can reach p' is deferred, with 'expected: reachable' on `never p` as the cheaper candidate. — An EF p kind would change the glossary meaning of Proved, Disproved, Evidence, Counterexample and Replay, and would need ADR 0008 and 0010 amendments. The guard needs no semantic change.
- F1 and F3 are labeled proposed ADR 0003 amendments, not clarifications. F1 lists three options: (a) any place, including generated places and states, (b) an observable place port, and (c) the property kept in the child's own scope. — Both reverse explicit choices in ADR 0003 or ADR 0002. Option (c) is sound for safety on children whose ports are all transitions.
- The TLA+ corpus figures were recomputed at a pinned commit with the regexes published. — This makes the figures reproducible. They now agree with the reviewer's independent rerun except for the liveness count, which depends on the regex.

## Proposed glossary changes

- **Property template**: A named, parameterized way to state one or more properties, for example 'At most k at once'. Each property it expands into is checked separately and has its own verdict; the template only shows a summary of them. _Avoid_: Pattern, query, formula, macro
- **Observer place**: A place the tool adds to a checked net to record history for one property, for example how often a transition fired. It never blocks a transition and discards tokens when full. (After v1.) _Avoid_: Monitor, ghost place, history variable, spec machine
- **Example**: A sequence of steps from the start that ends in a marking a 'can reach' property asks for. Only if a 'can reach' kind is adopted; that also requires changes to Proved, Disproved, Evidence, Replay and the Relationships line about counterexamples. _Avoid_: Witness, trace, scenario, run
